# RD09 隔离空白工作区恢复

恢复协调器只接受专用 RD09 临时根下显式创建的空目标目录。目标初始化时使用现有迁移器生成 025 基线，逐表确认只有迁移随附的默认账号和设置。V2 包通过认证后进入私有暂存，所有 42 张表的审核列在同一个 SQLite 事务内重建。候选关闭 WAL、校验关系与完整性，并复核逻辑行业务摘要、账号索引和每个 ready 素材的字节摘要。覆盖状态为 `partial`。现有 v1、JSON 备份和生产入口沿用现行契约。

数据库、账号索引和素材由同一个 generation ID 指向。独立 SQLite 写锁使同一目标的操作互斥。指针与双槽日志写入独占临时文件，完成文件同步后在同一目录重命名并复读。日志和指针保存操作 ID、阶段以及数据摘要。两代保留独立，切换前复验旧代和候选，切换后重新核验当前代。核验失败且旧代可确认时，记录 `ROLLING_BACK` 并整代切回。恢复中断必须明确选继续或回切。发现未知对象、截断、资源身份变化或矛盾的日志时，隔离读取和后续切换会失败，无法安全识别的对象保留待核查。

`PREPARED` 前的候选构造失败会清理能够核验身份的本次对象。构造过程中被强制结束、文件身份被替换或日志发布不确定时，可能保留私有暂存或候选。协调器可以检查可确认的旧代，但拒绝猜测孤儿目录的归属或自行重新导入。首次 `ACCEPTED` 或 `ROLLED_BACK` 为本次隔离操作的终点。另一次操作需要新空目标。

恢复沿用经审核的发送幂等、尝试、交付与素材状态。隔离操作入口只提供元数据检查，重开协调器仍读取持久化冻结。未知发送、历史 `running` 任务和原有排队状态没有获得执行授权。测试检查了 Native queue、renderer、Worker、AI、群轮询、发送重试和导出恢复等动作从隔离协调器收到 `RESTORE_FROZEN`。这些结果覆盖隔离协调器。侧车、WinUI、旧 renderer 和 Worker 的生产启动路径仍未接入代次控制。

## 验证范围

使用 Windows、捆绑 Node 和本地临时 SQLite。命令为 `node --test tests/device-migration-restore.test.cjs`。提交 `16f47b2` 通过 12/12，退出码 0，耗时 149.002 秒。用例实际写入和解包 V2，检查双账号同外部 ID、CRM 当前和历史记录、群成员归属、AI 相关记录与 ready/不可用素材，并断言导入前后的白名单表内容相等。其余用例覆盖已有任务拒绝、真实二级唯一索引冲突事务回滚、素材内容修改、候选文件身份替换、切换后验收失败、两侧进程中止、损坏日志、指针文件预重命名替换、锁文件缺失及第二进程的锁争用。夹具均为合成数据。

Windows 对照仅省略紧邻 `rename` 的文件身份复验。替换目标记录时，恢复错误地继续并完成。替换临时文件时，直到重命名后的复读才报告 `RESTORE_RECORD`。对照 0/2，退出码 1，耗时 19.006 秒。完整实现两例均在重命名前返回 `RESTORE_IDENTITY`，保留替代文件和已验证旧代，标识需要核实的恢复状态。
