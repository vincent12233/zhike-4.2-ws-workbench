# 独立扫码采集与本机群组管理

本轮用户要求优先恢复后台采集，并明确选择“独立采集会话，再扫码一次，聊天与采集同时运行”。这是源码改进；已发布的 `v6.1.0-rc.2` 安装包没有包含这些修改，原安装器的校验值和历史验收记录仍以当前版本索引为准。

## 会话与操作

每个账号分别保留前台聊天和独立采集会话。采集端使用新的账号专属数据目录，由用户在官方 WhatsApp 页面单独扫码登录。它不复制前台 profile、Cookie、IndexedDB 或 service-worker，也不复用历史复制产生的 collector 目录。

1. 在 WS 工作台选择需要采集的账号，打开“独立采集登录”。
2. 用当前所选账号的手机在采集页面扫码。应用按所选本地账号保存采集资料，请核对手机账号；前台聊天的已有登录保持独立。
3. 登录完成后返回聊天并启动采集。后台运行状态与前台“已连接”状态分别显示；前台登录成功本身不代表采集端已登录。
4. 在采集页面执行会话发现、已读历史采集，或配置需要观察的群组。保持未读跳过、群组范围和断点恢复规则。
5. 可暂停或恢复采集。关闭账号会释放其采集视图；清除账号会话同时处理该账号的前台及独立采集目录。

采集视图显示扫码页面时暂停自动采集。真实采集动作只在专用视图执行，不能回退到前台聊天。后台消息必须匹配宿主绑定的来源视图、账号和会话代次；页面自报 `collectorRole` 不构成授权。消息仍经过本地持久队列、去重和检查点处理。

该改动不启用生产 Worker 或自动 AI 消费者。采集完成不会自动发起付费 AI 请求；用户显式请求的 AI 操作继续使用已有确认流程。

## 群组管理的数据来源

生产环境可读取本机群目录、成员关系、同步记录和审计，不再因只读查询被统一挡在 Mock 开关之后。成员列表合并已有群成员记录与实际采集写入的权威客户群关系，并保留账号隔离、人工锁定和客户身份保护。

成员列表表示已观察并保存的关系，不保证等于 WhatsApp 的完整实时花名册。缺少可信阅读证据的消息保持“未知”，不能推断为已读。Mock 写入和模拟同步继续限于隔离测试；这些本地页面不会伪造 WhatsApp 邀请、移除成员或发送成功结果。

## 验证范围

验证使用合成账号、临时 SQLite 和平台替身，覆盖协议、账号隔离、profile 不复制、采集状态、生命周期及本地查询。不会读取用户真实数据库、复制登录状态或自动登录 WhatsApp。

本轮 Linux / Node 24.22.1 定向回归 **35/35 通过**，包括独立采集前端 16 个场景、旧版/未知能力拒绝 19 个场景、实际链接生产 C# 服务及来源鉴权的 13 个场景、真实 sidecar 群组查询，以及启动和数据兼容检查。另有 12 项现有采集脚本运行回归通过，覆盖未读跳过、历史分块、会话身份和虚拟列表。生产和隔离预处理路径均通过实际 WinUI/WebView 引用下的 C# 语义编译；这是带生成成员替身的检查，未替代 Windows XAML 构建。

新增 GitHub Actions Windows 工作流执行生产 WinUI 构建及定向隔离测试，不发布安装包、不访问真实账号。其结果应以对应提交的运行记录为准。

当前环境为 Linux，无法完成 WinUI/WebView2 Windows 原生构建和扫码实测。交付新安装包前仍需在受支持 Windows 上验证：独立扫码、双会话同时在线、前台输入不受干扰、后台实际采集与去重、暂停/恢复、断线恢复、账号切换、退出回收和安装升级。自动化结果不能代替这些实测，也不改变既有 S3 验收状态。

## 同分支的启动改进

全新空库的 22 个登记迁移在一次事务中初始化；元数据、schema 和版本同时提交。失败或进程中断后完整回滚。已有 schema 的数据库继续按原来的逐版本事务升级。历史迁移文件、checksum、备份和完整性检查保持原规则。

可直接使用 Node 24 运行 `node scripts/stage1/migration-runner-fresh-atomic.test.cjs`。该测试比较 42 张业务表，并覆盖失败回滚、进程中断、并发读取、备份、幂等和旧库升级；已加入 `stage5` 和 `all` 回归入口。它不证明 Windows 首次启动耗时改善，也不能代替原生验收。
