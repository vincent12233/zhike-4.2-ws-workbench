# 知客 6.1 队列映射冻结版设计审查

审查日期：2026-11-15  
审查范围：`C:\Users\酷酷\Desktop\知客6.1_A+B_最终技术设计_队列映射冻结版.md` 及当前 6.0.3 仓库实现  
审查结论：设计基线已更新；生产实施仍被 P0 门禁阻断。

## 1. 已确认并可作为基线的内容

- 采用 A+B：保留现有 WinUI 3、WebView2、SQLite 和业务页面，新增独立 Worker，前台 WS 聊天与后台采集隔离。
- 知客主侧边栏保留；WS 使用独立侧边栏和独立工作区。
- 普通聊天 AI 只补齐唯一匹配客户的有证据空字段，不自动建陌生客户；独立群组入群登记是单独的确定性规则链路。
- 设备迁移不复制 Cookie、Token、WebView 登录态或 AI Key；新设备重新扫码和配置密钥。
- 迁移、双读校验、单写入者切换、灰度和回滚必须先于生产 Worker。
- 普通群、VIP 群、单导、FB 群粉等来源必须保留稳定来源定义，缺少来源时显示“未分类，待绑定”。
- 事件必须保存 `occurredAt` 与 `observedAt`，未知事件不能伪造时间；群关系按账号和群组独立维护。

## 2. 当前仍未达到“队列映射已冻结”的项目

### P0：必须在阶段 0/1 前补齐

1. **真实旧表与写入者清单未落地。** 文档列出 `ws_collection_runs/items`、现有 AI 队列和 `ws_ai_analyses` 的映射方向，但仍要求“以代码审计确认实际表名”。必须提交逐表、逐字段、逐状态映射和实际行数/异常报告后，才能冻结 020/021。
2. **CRM 单一事实源未落地。** 当前客户主档同时存在 `customers`、`app_state` 投影和 WS 关联 JSON；新领域表的权威、回填、反向投影、双写停止点和回滚路径仍未定。
3. **Checkpoint 与待审核事件语义冲突。** 当前群事件实现可能在 `pending/review` 仍推进 checkpoint；新规则要求客户关联成功后才推进。必须冻结“事件落库、人工处理、重放、checkpoint 提交”的状态机。
4. **事件幂等键需要升级。** 现实现使用短 FNV 组合键；必须改为平台事件 ID，或使用包含账号/群/成员/游标/时间/原文证据的抗碰撞哈希，并提供旧键迁移审计。
5. **账号和权限边界未实现。** 现有 API 仍存在省略 `accountId` 查询全部账号、全账号导出等兼容路径；必须定义聊天操作员、群管、导出和管理员的 capability、账号/群组范围及旧接口兼容策略。
6. **Worker 授权会话边界未冻结。** 当前代码仍有“从前台 profile 复制到 collector profile”的旧路径；新 Worker 必须在启用前彻底禁用该路径，采用独立授权会话，并定义扫码、失效、撤销和重建状态机。
7. **IPC token 生命周期未冻结。** 现有 sidecar 重启可能复用旧 token；必须定义每次启动轮换、旧 token 撤销、握手、重放保护和权限上下文。

### P0：迁移和跨设备发布仍未闭合

8. **`.zkdevice` 格式未冻结。** 需单一 KDF、参数、版本、nonce/salt、分片格式、临时文件清理、原子替换/合并、ID 冲突和媒体路径重写，并提供 .NET/Node 互操作测试向量。
9. **6.0.3 旧备份兼容未定义。** 现有 JSON/旧 WS 导出如何转换为 `.zkdevice`、失败如何提示、旧接口何时禁用，必须形成一次性转换和回滚方案。
10. **导出/导入内容不对称。** 当前旧导入路径未完整恢复群组、发送审计、媒体、联系人和 CRM 作用域；设备包必须采用流式协议、事务性导入和逐项恢复报告。
11. **并发迁移屏障未定义。** 导出前需暂停/排空 Worker、完成 WAL checkpoint、记录 outbox 高水位和恢复点，导入后再恢复；不能只记录一个快照时间。
12. **版本锁和安装产物未闭合。** 迁移 runner 目前是硬编码旧版本链；必须支持动态迁移、拒绝高版本库、6.0.3→6.1 转换，并把 Worker、群管、看群、manifest、运行库检查纳入安装包白名单和干净机验收。
13. **删除传播策略未定义。** 账号、客户、成员关系、排除名单在迁移合并时的 tombstone、版本向量和“禁止旧包复活”规则必须冻结；默认应先支持空工作区导入，已有数据只允许 dry-run 后按明确策略合并。

## 3. 当前代码审计得到的运行风险

- 前台 WebView 仍存在 ResizeObserver/内容变化驱动的宿主尺寸调整，可能造成 WS 周期性抖动；固定聊天视口和后台采集零 DOM 控制必须在 P0 修复。
- 全局 wheel 捕获与 WS 宿主 `touch-action:none` 存在双重滚动所有权，内外层滚动会互相抢事件。
- WebView session pool、采集轮询、全量状态序列化、`pending.json` 全量重写和启动时全量修复仍有规模化性能风险。
- 前端刷新逻辑存在全视图重绘路径，可能丢失焦点和滚动位置；需改为按账号/会话/卡片增量更新。

## 4. 实施前必须交付的审计包

1. 当前数据库 schema、表行数、状态分布、索引、触发器、孤儿和重复键报告。
2. 旧队列/AI/群事件的逐字段映射合同和状态转换表。
3. CRM 权威与投影切换图，含回填、双读、单写入者和回滚演练。
4. 账号/角色/capability/IPC 会话矩阵及旧 API 收敛方案。
5. `.zkdevice` v1 加密格式、旧备份转换、流式导入和并发快照协议。
6. Worker 阶段 0 隔离验证报告：启动、停止、取消、心跳、崩溃恢复、资源占用和前台无抖动证据。

在以上交付物完成并经批准前，不创建 020/021/025–030 的生产并行表，不启动生产新 Worker，不做双写，不生成“已完成”的 6.1 安装包。

## 5. 追加核对项

- 现有群监测目标的唯一键按 `profile_id + group_jid`，而群目录按 `account_id + group_jid`；迁移前必须合并重复 profile/target/checkpoint，并固定事件归属。
- 现有群登记路径可能把群关系状态直接投影到客户全局 `status`；6.1 必须改为关系级事实和派生只读视图，不能覆盖人工状态或其他业务状态。
- 当前来源定义仍主要来自 `app_state.settings.sourceDefinitions`，缺失来源可能回退成泛化“群粉”；来源实体、历史映射和“未分类，待绑定”必须先落库。
- 当前导出文件仍存在明文 JSON、过期下载和清理闭环不足；旧导出接口必须在 `.zkdevice` 流程上线前收敛或隔离。
- 当前没有成员级已读/送达证据链；阶段 0 若实测不可用，后续看群统计必须降级为 `SourceLimited`，不得创建假数据表或假已读率。
- 6.0.3 的原地升级与“只通过 `.zkdevice` 导入”两种兼容语义必须二选一并写入发布门禁；不能让安装包、旧数据根和迁移工具各自采用不同规则。
- 所有 Worker/IPC/旧 API 兼容包装都必须统一携带 `schemaVersion`、`requestId`、`accountId`、权限上下文和幂等键，防止新群管事件绕过新权限和幂等路径。
