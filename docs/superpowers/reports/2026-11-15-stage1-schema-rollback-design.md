## 4. 备份与快照格式

迁移前必须在停止所有 SQLite 写入者后生成一致性快照：

1. 写入协调者进入 `draining`，拒绝新写事务，等待在途批次完成或取消。
2. 执行 `PRAGMA wal_checkpoint(TRUNCATE)`（失败即停止迁移，不继续复制）。
3. 使用 SQLite 在线备份/只读副本生成 `workspace.sqlite.<timestamp>.<schema>.bak`，同时保存 `PRAGMA integrity_check`、`foreign_key_check`、`user_version`、行数、SHA-256 和应用版本。
4. 备份清单写入独立 manifest，不放入业务表，不包含 API key、Cookie、Token 或 WebView 登录态。
5. 备份成功后才允许在临时数据库上执行迁移；原库保持不变，直到验证完成。

设备迁移包 `.zkdevice` 另有加密、哈希和人工确认流程；它不等价于 SQLite 备份，也不能复制 WhatsApp 登录态。

## 5. 回填与校验

回填必须是可暂停、可重试、可审计的离线作业：

- 每批带 `migration_id`、`source_schema`、`source_high_water_mark`、`batch_id` 和结果摘要。
- 以旧主键和批准的稳定幂等键写入目标；重复执行只能得到 `existed=true`/相同结果。
- 验证总行数、按账号/状态分布、主键/唯一键冲突、孤儿外键、分析/任务/证据引用、checkpoint 单调性、消息方向和客户 ID 关联。
- 差异按 `missing/duplicate/conflict/unmapped` 分类；任何未解释差异都阻止切换。
- 失败只重试当前批次，不推进全局水位；回填日志不得写入生产业务表。

## 6. 失败恢复与回滚

### 迁移失败

在临时副本中失败：丢弃临时副本，保留原库和错误报告。生产迁移失败：立即撤销写入 lease，恢复迁移前快照，运行完整性检查和只读对账，确认旧应用可启动后才恢复旧写入者。

### 切换后发现问题

先停止新 Worker/新 writer，隔离新产生的目标任务和 outbox（不删除），保存故障快照；若旧 schema 可读，则切回旧兼容写入；若已发生不可逆 DDL 或目标写入，必须从切换前快照恢复，禁止“仅切 UI flag”伪回滚。

### 升级/卸载

安装升级不得删除用户数据；卸载必须明确提供“保留数据/清理数据”选择。旧版本恢复使用完整安装包 + 对应快照，不支持把新 schema 静默降级为旧 schema。
