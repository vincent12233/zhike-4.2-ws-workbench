## 2. 平台支持边界

截至本次官方文档核查，不能笼统写“官方完全没有群组 API”，也不能写“扫码登录后即可获得全部群控能力”。

- **P1：账号接入不同。** 官方已有 Groups API，但要求 OBA 资格，文档当前列出每群最多 8 人，并排除 WhatsApp Business App 号码。现有个人/扫码 WebView 会话不自动获得这些资格或接口；本项目未证明已有可用适配。[Meta Groups API](https://developers.facebook.com/documentation/business-messaging/whatsapp/groups/)
- **P2：逐动作核对。** 官方参考包含邀请链接、移除成员等接口；不能强行直接添加参与者。`Update group settings` 当前列出的参数是群主题、描述、图片，不能据此推导“禁言/设管理员”已支持；重置邀请链接会使旧链接失效。此接口范围也不是任意既有 Web 群的能力证明。[Meta Group management reference](https://developers.facebook.com/documentation/business-messaging/whatsapp/groups/reference)
- **P3：人工界面不等于批量接口。** WhatsApp Web 帮助确有手动邀请链接操作，权限取决于群设置等条件；“用户能在 Web 上手动做”不能代替本项目自动化命令、身份校验和真实验收。[WhatsApp Web 群组与邀请说明](https://faq.whatsapp.com/3242937609289432/?cms_platform=web)
- **P4：发送对象与授权。** 群发设计需要确认收件来源、联系许可和退出处理，并核对所选平台接口的使用条件；本地限速数字不是平台许可证明。[WhatsApp 负责任使用说明](https://faq.whatsapp.com/361005896189245/?eea=0&locale=en_US)

以上只用于准备能力验证。**本轮不批准切换为 Cloud API、不新增第三方非官方 SDK、不执行 DOM 批量群操作、不复制 Cookie/Token/WebView 登录态。** 若保留扫码 Web 路径，必须对每项能力证明安全可用；若选择官方业务 API，需另行确认账号资格、授权方式、群适用范围、费用和迁移影响。

## 4. 十四项逐项盘点

以下“新增”均为待确认建议，不是已经开发或获准执行的接口。

### F01 多账号群发 — 部分实现

**现有 UI/服务：** `ws-workbench.js:689–703,2963,4706,4755`，当前加载的一对一已读会话最多选择 50 条；创建计划后，逐目标人工打开对应前台会话并确认。文本、图片/文件等附件的选择和计划引用存在。链路为 `POST /api/ws/broadcast`（`server.mjs:4297`）→ 计划/审计 → Native `send-text/send-media` → `POST /api/ws/send`（4370）登记本地结果；sidecar 不直接连接远程 WS。Native `BroadcastWsTextAsync:1518` 的循环也不会自动切账号或会话。

**隔离/权限/审计：** 计划、会话、媒体按账号查询；`SendWsTextAsync:1422`、`SendWsMediaAsync:1462` 检查人工确认、当前前台账号及会话。已有 `ws_send_audit`、`ws_send_attachments`。这是本地发送动作审计，不是平台送达确认，亦非多账号后台调度。

“已读”目前是 UI 候选筛选，`server.mjs:1772–1778` 仅验证账号/会话及一对一类型，未检查未读计数；不能声称服务/Native 已提供全链路未读保护。新导入/消费者应按已确认政策补统一校验。另 `ws-workbench.js:4732,4785` 的媒体说明取 caption/原文，翻译预览并不证明附件说明会使用译文，需明确原文/译文选择契约后测试。

**缺口与依赖：** 账号分配、目标去重/排除、任务恢复、逐附件确认、暂停/取消、结果不明对账、可靠回执。若仅整理当前人工模式，可复用现有服务且未必迁移；若增加持久多账号计划，需评估计划/目标/附件状态结构及单消费者、fencing、取消。当前 Native 人工发送路径不经过新 Worker fencing，不能直接扩大为后台发送。

**平台/后果：** 真正多账号自动执行尚未验证，参见 P1/P4；发送不能由数据库回滚撤销。不得抢占用户前台聊天，也不能把本地点击成功显示成已送达。

**独立页面/难度：** “群发中心”完整页面：计划列表、账号分配、目标/排除预览、内容/附件预览、逐目标结果和审计。保留人工确认模式为中；多账号可恢复自动调度为高，先做能力验证。实施前须处理第 6 节 R01–R06。

## 7. 独立页面与交互实施准备

保留既有十二页主结构和设计系统，建议完整子页归属如下；是否调整 WS 二级导航数量需确认：

| 归属 | 建议完整页面 | 内容及边界 |
| --- | --- | --- |
| 数据采集/工具 | 群发中心、导入任务、计划详情 | 账号范围、预览、排除、确认、逐项结果；不能隐藏在狭窄抽屉 |
| 通讯录管理 | 本地目录、导入批次/预览、联系人详情 | 读目录与写入目标分开，来源/规范号码/重复/未匹配明确 |
| 群组管理 | 群操作中心、加入/退出任务、邀请链接 | 表格主区充分利用空间，右侧详情可关；高风险动作分开确认 |
| 群成员管理 | 移除计划、角色变更计划 | 先锁定账号与群，再选择成员，展示权限与差异 |
| 工具与设置 | 个人素材库、翻译、AI服务与密钥、运行诊断 | 每项使用完整内容页，敏感凭据掩码，监测只读 |
| AI助手 | 任务/证据/结果、助手配置（若确认） | 新管理与现有任务、GPT工具明确区别，不导航即启用消费者 |

通用流程建议为“选择账号/范围 → 校验能力和权限 → 预览计划/排除项 → 明确确认 → 执行与逐项结果 → 对账/审计”。这是待评审交互，不是已实现的任务状态机。

批量操作必须显示已选数量、隐藏筛选外选项策略和预计影响；重复点击、防迟到响应、切号清理及可取消阶段均需设计。取消只停止尚未发生的动作，不能谎称撤销外部结果；请求超时不能直接当成平台未执行。前台聊天实例与用户操作仍独立，任何执行不能抢占会话、滚动或导航。

## 8. 建议开发顺序与范围门禁

1. **先确认语义和技术路线。** 确认第10节范围；对F01自动发送和F04–F09做独立能力验证，不以UI或Mock取代。探针需单独授权，仅隔离/明确测试账号，不触及生产。
2. **先消除复用路径的风险。** 受控复现R01–R09，优先数据完整性、账号/凭据绑定、外部结果不明和单消费者；每项最小修复配专项回归，不能借新增功能扩大旧问题。
3. **本地高复用批次。** 联系人/群发导入预览、素材管理、密钥/翻译设置整理、只读运行诊断；不默认写CRM/平台，不新增正式消费者。各页独立交付。
4. **发送计划批次。** 先明确的已知会话人工确认模式；只有可靠平台执行和结果证据具备后才评审多账号耐久自动执行。不得先做自动切换去操作用户前台。
5. **群组读取批次。** 邀请链接等只读能力在相应接口/权限证实后实施；隔离快照不能作实时权限。
6. **群组外部写入批次。** F04–F08逐动作批准、设计、验证。没有可用的安全平台能力时应保留“不可用/未验证”，不交付假按钮。权限提升、退出、移除等单独验收。
7. **新助手管理批次。** 提示词版本/绑定/预算如被确认，复用现有AI权威；正式消费者启用及真实质量验收另行批准。

每批次先专项与原生验证，再运行必要安全/回归；最后综合验收。不重复阶段0–5已完成架构，不因“合并批量队列”而重写已有业务。
