# 知客 6.1 阶段 0 Worker 可行性验证实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: 使用隔离探针和只读审计；不得连接生产账号或修改生产数据库。

**Goal:** 在隔离临时目录中验证独立 Worker、IPC、取消、心跳、崩溃恢复和资源观测链路，并完成现有 WS/AI 队列的只读映射审计。

**Architecture:** 保留现有 6.0.3 生产运行路径不变。阶段 0 只增加测试/审计工具：一个临时 Worker 探针使用动态 loopback 或命名管道，使用临时 SQLite/JSON 状态；一个只读 schema/写入路径审计生成映射报告。所有验证结果可重复、可清理、可回滚。

**Tech Stack:** .NET 8/WinUI 现有本机服务管理器、Node.js sidecar、SQLite、PowerShell/Node 审计脚本、现有 `scripts/run-tests.cjs`。

**Spec:** `docs/superpowers/specs/2026-11-15-zhike-6.1-a-plus-technical-design.md` 第 6.1、7、13、14、15 节。

## Global Constraints

- 不创建 019–030 生产迁移表，不修改生产 schema，不执行双写。
- 不连接真实 WhatsApp/WS 账号，不复制 Cookie、Token、WebView 登录态，不调用真实 AI。
- 所有临时数据放在系统临时目录或测试专用目录，测试结束自动清理。
- 生产代码路径保持行为不变；若新增代码只能是隔离探针或测试工具。
- 任何“通过”结论必须有命令、退出码、日志和失败注入证据。

## Review Focus

- Worker 崩溃或 sidecar 重启后，租约/心跳/任务状态是否可恢复，且不会产生第二个有效执行者。
- 调用方取消、超时、重复 requestId 和失联重连是否安全收敛。
- 动态端口/命名管道是否避免固定端口、跨用户访问和旧 token 重放。
- 临时 SQLite 写入是否保持单写入者、幂等和 checkpoint 顺序。
- 现有旧队列/AI 表是否能逐字段映射；若不能，必须输出阻断项而不是猜测。

## 执行记录

- Ruling：不新增 `run-stage0.cjs` 总包装器。阶段 0 使用两个可独立复现的入口（`worker-probe.cjs` 与 `audit-queue-mapping.cjs`），避免包装器吞掉子进程退出码或把只读审计误解为生产运行；代价是验收时需分别运行两条命令。
- Ruling：不建立脱敏副本行数回填工具。当前仓库没有授权的运行时数据库副本，阶段 0 仅完成源码/schema/写入者审计；代价是历史数据分布仍需在取得脱敏副本后由阶段 1 复核。
