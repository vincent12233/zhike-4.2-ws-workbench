# 知客 6.1 P0 基础设施受控整改实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不触及生产数据库、真实 WS 登录态或正式 Worker 的前提下，修复并隔离验证知客 6.1 A+B 的六项 P0 基础设施阻断。

**Architecture:** 保留现有本地 SQLite/WinUI/sidecar 业务边界，先把迁移和写入协调抽成可测试的基础设施边界，再让 AI/CRM/群组路径复用同一事实写入合同。所有验证使用临时 SQLite、临时迁移目录和隔离 .NET 进程；旧队列继续作为唯一生产事实来源，feature flag 保持 legacy。

**Tech Stack:** Node.js 24 `node:sqlite`、ES modules/CommonJS、SQLite WAL/事务、.NET 10 Windows Named Pipe、现有 WinUI 3 host。

## Global Constraints

- 不修改生产 SQLite、客户数据、群组数据、消息数据或真实 WS 登录态。
- 不启动正式 WS Worker、AI Worker，不启用新 outbox，不执行新旧队列双写。
- 数据库结构通过统一版本化迁移管理；测试迁移只能写临时目录。
- 不复制 Cookie、Token 或 WebView 登录态；IPC token 只存在隔离进程内存。
- 保留现有业务规则、旧队列数据、`ws_ai_analyses` 历史结果和人工客户字段。
- 每个 P0 单独测试、单独提交、可独立回滚；每项完成后运行相关回归。

## Review Focus

- 已有数据库在 018、重复启动和迁移失败时不能重复或损坏；由 Task 1 的 migration runner isolation test 覆盖。
- 已完成 AI 任务不能因 schema 回填重新进入队列；由 Task 2 的 historical job/evidence test 覆盖。
- 两个并发群组登记不能产生两个客户，且退一个群不能覆盖客户全局状态；由 Task 3/4 的 SQLite concurrency/relationship tests 覆盖。
- Worker 失联后旧 fencing token 不能提交事实或 checkpoint；由 Task 5 的 writer lease integration test 覆盖。
- IPC 重启、旧 token、不同 SID 和日志输出不能越权或泄露凭据；由 Task 6 的 .NET Named Pipe integration test 覆盖。
