# 知客 6.1 A+B 最终技术设计（整合版）

> 状态：完整设计草案，尚未实施或完成真实验收。基于原《知客 6.1 A+B 技术设计》整合新增独立 WS 群组管理、自动登记、看群统计和通用 Windows 安装要求。本文档需在代码审计和技术可行性验证后批准实施。
> 版本：整合修订稿 2026-11-15；原设计的审计结论和 205 项测试属于原文陈述，尚未由本次文档编制独立复测。

## 1. 目标与硬约束

### 目标

在不破坏知客现有业务规则和数据的前提下，把 WS 工作台升级为可长期运行的多账号运营工作台：前台聊天与后台采集完全隔离，采集结果可靠地进入客户档案、AI 队列和跟进任务；应用可以在新设备安装，通过受保护的设备迁移包恢复业务数据；界面、滚动、资源占用和错误恢复达到正式桌面软件标准。

### 硬约束

1. 知客主侧边栏、现有客户、群组、VIP、跟票、报名、入金、统计、GPT、手机号登记规则保持不变。
2. WS 使用独立侧边栏，只在 WS 工作区内部显示；不得替换、重排或复用知客主侧边栏。
3. 保留 WinUI 3 + WebView2 + 本机 SQLite 运行线，不恢复 Docker、Electron 或旧客户端。
4. 不复制 Cookie、Token、密码或其他敏感登录凭据；不绕过 WhatsApp 平台限制。
5. 不使用生产模拟数据、虚假按钮、空函数或固定返回值伪装正式功能。
6. 任何数据迁移、数据库变更和高风险重构都必须可回滚，并保护客户、群组、消息和业务记录。
7. 未读会话不自动打开；后台采集不得操作前台 WebView 的 DOM、焦点、滚动或窗口尺寸。
8. **普通 WS 聊天 AI**只补齐已唯一匹配客户的有证据空字段，不自动创建客户；**独立 WS 群组管理的确定性入群登记服务**可依据已验证的成员身份及既定登记规则自动创建新客户，已有客户只关联或更新群组关系，不重复建档。低置信度、冲突和无法匹配的记录进入可见人工处理队列。
9. 自动化测试通过不等于真实验收完成；真实 WS、真实 AI、长时间运行、安装包和跨设备迁移必须单独验收。

## 2. 当前审计结论

6.0.3 当前自动化基线为 205 项通过，工作区无未提交修改。审计发现下列问题必须在 6.1 解决：

### P0：阻断性或数据风险

- `/api/ws/export` 已输出群组、成员事件、发送审计、联系人和媒体索引，但 `/api/ws/import` 没有完整恢复这些段，媒体二进制也未进入设备包。
- WS 账号存在 SQLite、`accounts.json` 和 WebView profile 三个来源；远端删除或本地“忘记账号”可能在下次加载时复活。
- `WsRuntimeService` 以 UI Dispatcher 的 10 秒定时器每次只租用一个后台账号；WebView 会话池容量固定为 3，多账号会轮换重建并产生资源峰值。
- 后台采集在进入 WS 路由后才激活，应用重启后不能保证自动恢复。
- 采集 profile 通过复制运行中的 WebView 目录建立，认证存储在复制期间可能不一致。
- WebView ResizeObserver、全局 capture wheel、`touch-action:none` 和多层动画共同造成前台 WS 间隔闪动、滚轮串区和输入延迟。
- collector 对整个 body 做 MutationObserver 和完整 DOM 扫描，多账号时 CPU/GPU/磁盘压力随会话数增长。

### P1：规模、可靠性和维护风险

- `/api/state` 和 native fallback 仍会序列化或解析完整 CRM 状态；客户量增大后会阻塞 Node 和 WinUI。
- AI 处理依赖前端队列泵；sidecar 重启后导出任务没有同等的恢复和游标机制。
- 会话、消息和预览存在隐式数量上限，超过上限会出现部分结果，需要改为可续传的明确状态。
- 群组监测主要读取已渲染 DOM，未渲染历史事件无法保证覆盖；渠道元数据缺失时可能合并为泛化“群粉”。
- WS、server、原生宿主和 CSS 文件过大，局部修补会继续增加耦合。

### P2：视觉、兼容性和发布风险

- 首屏加载约 18 个 CSS 和 25 个脚本，多层 `!important` 和重复媒体查询会造成样式串扰。
- 背景 PNG 体积较大，没有按路由懒加载；连续光效会触发不必要重绘。
- 小字号辅助文字对比度不足，焦点样式和动态状态语义不统一。
- 安装包自包含 WinUI，但仍依赖目标设备的 WebView2 Runtime。
- 运行时 `workspace.sqlite-wal/shm` 等产物必须与源码和发布包隔离。

## 3. 方案选择

### 方案 A：稳定演进

保留 WinUI 3、WebView2、本机 SQLite 和现有业务页面，把 WS、AI、档案、任务和数据访问按领域拆分，逐步把全量状态 Blob 降为兼容入口。该方案的优点是数据和业务风险最低。

### 方案 B：WS 独立采集 Worker

在方案 A 的基础上，将后台采集、群组监测、采集 checkpoint 和采集指标放入独立 Worker。前台 WebView 只承担用户聊天和可见交互，通过本机 IPC/SQLite outbox 与 Worker 通信。该方案解决 UI 线程阻塞和前后台互相影响的问题。

### 采用：A+B

先以小型 Worker 技术验证确认独立进程、IPC、取消、重启和资源隔离可行，再按领域逐步迁移正式功能。不会在没有 Worker 验证的情况下重写整个项目，也不会先做视觉替换再暴露底层数据问题。

## 4. 目标模块架构

```text
┌──────────────────── 知客 WinUI 主应用 ────────────────────┐
│ 知客主侧边栏（保持不变）                                   │
│ ┌──────────── WS 独立侧边栏 ────────────┐                  │
│ │ 账号 / 会话 / 群监测 / 群发 / 导出      │                  │
│ └──────────────────────────────────────┘                  │
│ 前台 WS WebView  ←→  WsUiBridge  ←→  本机 SQLite API       │
└──────────────────────────────┬───────────────────────────┘
                               │ IPC + durable outbox
                     ┌─────────▼─────────┐
                     │ WS Collector Worker│
                     │ 多账号公平调度      │
                     │ 联系人/列表/历史     │
                     │ 群组监测            │
                     │ checkpoint/指标     │
                     └─────────┬─────────┘
                               │
                     ┌─────────▼─────────┐
                     │ SQLite sidecar     │
                     │ 事实表 + 事件表     │
                     │ AI/任务/导出队列    │
                     └─────────┬─────────┘
                               │
             ┌─────────────────▼─────────────────┐
             │ AI Worker / CRM Linker / Task Sink │
             └───────────────────────────────────┘
```

### 模块边界

- `WsAccountRegistry`：SQLite 账号权威、版本、删除和本地缓存对账。
- `WsWorkerSupervisor`：Worker 启停、槽位、健康、崩溃恢复和资源预算。
- `WsCollectorWorker`：只读采集、会话游标、消息/联系人/群组发现、未读跳过。
- `WsCollectorBridge`：IPC、批次确认、取消、重试和错误分类。
- `WsArchiveLinker`：普通聊天 WS 身份与客户主档的安全关联，不创建陌生客户；独立群组登记使用单独的受控服务。
- `AiQueueWorker`：持久任务、分段分析、证据、置信度、冲突和重试。
- `FollowupProjection`：今日工作台、任务中心、阶段看板的统一待办投影。
- `WsExportMigration`：设备包、媒体、哈希、加密和导入报告。
- `WsUiShell`：WS 独立侧边栏、前台 WebView、辅助抽屉和流程条。

## 5. 数据流设计

```text
WS 前台聊天
  └─ 只处理用户当前会话和发送操作

后台 Worker
  └─ 联系人/列表增量
       └─ 会话历史增量
            └─ 双方消息、方向、外部 ID、群事件
                 └─ SQLite 事实表（幂等写入）
                      └─ 客户匹配/群组关系
                           └─ AI 队列
                                ├─ 字段证据与置信度
                                ├─ 客户空字段补齐
                                └─ 跟进任务投影
```

所有链路都携带 `accountId`、`conversationId`、`sourceCursor` 和 `schemaVersion`。前台 UI 订阅增量事件，只刷新对应账号、会话或卡片，不重新渲染整个 WS 宿主。

## 6. 数据库与迁移方案

### 原则

- 只追加迁移，不删除现有业务表和数据。
- 每次迁移前生成可验证快照；迁移失败自动回滚。
- 迁移脚本必须幂等，避免仅依赖 `user_version` 判断列是否存在。
- 启动阶段只检查版本，不做全量客户、消息或预览修复；修复改为可暂停的后台作业。
- 6.0.3 兼容 API 在过渡期继续提供，6.1 页面逐步改用领域 API。

### 计划迁移

| 迁移 | 内容 | 目的 |
|---|---|---|
| 019 | `ws_account_registry` 扩展 `background_enabled`、`collector_state`、`profile_version`、`sync_revision`、`deleted_at` | 统一账号权威与删除状态 |
| 020 | `ws_collector_jobs`、`ws_collector_checkpoints`、`ws_worker_heartbeats`、`ws_collector_events` | Worker 可恢复调度和断点 |
| 021 | `ws_ai_outbox`、`ws_ai_attempts`、`ws_ai_evidence` 补充租约、取消、重试、模型和证据哈希 | AI 队列持久化 |
| 022 | `ws_export_jobs` 增加游标、快照水位、临时文件、恢复状态 | 导出重启恢复 |
| 023 | 群组来源定义、账号/群组/渠道稳定 ID 及复合索引 | 防止单导、FB 群粉等渠道合并 |
| 024 | 账号、时间、置信度、会话和消息分页索引 | 支持规模化查询 |

### 数据兼容

6.0.3 的 `app_state` 仍作为兼容投影，但新写入只保存设置、视图和迁移标记。客户、业务、WS、AI 和任务事实写入领域表；所有回填使用批次、游标和可恢复状态，不能在启动时长时间占用 UI 或 sidecar。

### 6.1 P0：旧采集队列与 AI 表映射、回填和单写入者切换门禁

**当前状态：设计冻结；未批准正式迁移。** 迁移 020、021 是候选目标结构，不构成立即创建生产并行表或启动新 Worker 的授权。必须先对真实仓库 schema、现有读写代码、状态机、唯一约束、历史数据量及失败恢复路径完成审计，形成逐字段映射与数据流图。

| 旧来源 | 目标设计 | 迁移前必须确认 |
|---|---|---|
| `ws_collection_runs` | `ws_collector_jobs`、`ws_collector_checkpoints` | run/job 身份、账号与会话作用域、状态、开始/结束时间、游标、失败次数、取消、恢复语义 |
| `ws_collection_items` | 新 Worker 的任务项/采集事实/事件或 checkpoint 关联 | item 唯一键、来源消息/成员 ID、完成确认、重复项、重试、批次边界与历史追溯 |
| 现有 AI 队列（以代码审计确认实际表名） | `ws_ai_outbox`、`ws_ai_attempts` | 排队/执行/重试/失败/取消状态、任务所有者、租约、模型、输入哈希、执行次数 |
| `ws_ai_analyses` | `ws_ai_evidence` 及必要的分析结果兼容视图 | 分析 ID、客户 ID、消息证据、字段、旧/新值、置信度、模型、时间、人工确认与冲突状态 |

**强制执行顺序：**

1. **现状盘点与冻结：** 枚举所有旧表、触发器、索引、前端队列泵、sidecar/API 写入路径及定时任务；记录旧表行数、状态分布、孤儿记录、重复键和失败任务。未确认真实 schema 时，不臆造字段或直接执行 DDL。
2. **映射合同：** 为每个旧字段、状态和关系定义目标字段、转换规则、不可映射情形、默认值依据、审计来源及回退读取方式；特别保证 `ws_collection_runs/items` 与 AI 任务、分析结果之间的引用可追溯。
3. **唯一键兼容：** 对旧/新任务建立稳定的迁移映射 ID 和幂等键；检查现有唯一约束与目标复合键是否冲突。冲突、重复、缺失关联必须形成报告，不得静默合并、丢弃或生成新的 AI 执行任务。
4. **隔离环境回填：** 先用生产数据的一致性脱敏副本进行可重复的批次回填，记录高水位、行数、状态、校验和、孤儿关系及错误清单；回填不得触发 WS 采集、AI 调用、客户字段修改或消息发送。
5. **双读验证：** 通过只读兼容适配器同时查询旧结构和目标结构，逐账号、任务状态、时间区间、关联记录比较数量与关键字段；差异必须解释并达到经批准的零未解释差异门禁。**双读不等于双写。**
6. **单写入者切换：** 建立持久的队列写入所有权/世代号与 feature flag。先停止并排空或安全暂停旧前端队列泵，撤销旧写入租约，确认没有旧写入者；再在受控事务/切换协调流程中启用新 Worker 写入。任何时刻同一逻辑任务只能有一个权威写入路径，不允许旧前端与新 Worker 各写一套表。
7. **灰度与回滚：** 先限定测试账号/工作区灰度，持续比较旧兼容读取与新权威结果，验证无重复采集、无重复 AI 执行、无任务丢失。回滚时先停新写入并隔离新任务，再按明确的版本与数据兼容策略恢复旧写入路径；不得仅关闭 UI flag 就让旧代码读取不兼容数据库。

**切换门禁与交付物：** 提交旧→新字段/状态映射表、DDL 差异、唯一键冲突报告、回填脚本及幂等复跑结果、双读对账报告、写入者切换状态机、feature flag 方案、故障注入测试、回滚演练记录。未全部审核通过时保持设计冻结：**不在正式数据库创建并行队列表，不迁移生产队列，不启动生产新 Worker，不允许双写。** 隔离测试数据库内的 Worker/IPC 可行性实验不受此限制，但不得连接生产数据或账号。

## 7. Worker 生命周期

### 启动

1. WinUI 启动本机 sidecar 并等待健康状态。
2. 读取 SQLite 账号权威集合，校验 schema 和上次 Worker 租约。
3. 与本地显示缓存进行双向对账；远端已删除账号不会复活。
4. 只恢复 `background_enabled=true` 且未被用户暂停的账号。
5. 启动 Worker Supervisor，前台 WS 页面是否打开不影响后台任务。

### 运行

- 默认 2 个采集槽位，支持在资源预算内配置 1–4 个。
- 每个账号按 `nextProbeAt`、失败退避和任务优先级公平轮换。
- 当前账号进入前台聊天时，Worker 不触碰其前台 DOM；聊天窗口由独立 WebView 会话负责。
- 每个批次写入 checkpoint，成功后才推进游标；失败只重试当前批次。
- 所有状态都可在 WS 独立侧边栏查看：运行、暂停、等待登录、限流、失败、最后心跳、队列深度。

### 停止与恢复

- 关闭 WS、退出应用、关机和休眠时写入租约和 checkpoint。
- Worker 崩溃由 Supervisor 有限次数重启；连续失败转为需人工处理，不循环占用资源。
- sidecar 重启时恢复 queued/running AI 和导出任务，清理过期 `.part` 文件。

### 登录安全

Worker 不复制前台 Cookie、Token 或密码。后台采集使用独立的 WebView profile；首次启用某账号的采集会显示明确的“后台采集会话授权”并要求用户扫码登录，登录态由 WebView2 自己保存。换设备必须重新扫码。若平台页面不允许稳定的独立会话，功能必须显示“需重新授权”，不能通过读取或复制敏感凭据绕过。

## 8. 多账号管理

- SQLite `ws_account_registry` 是唯一权威来源；`accounts.json` 只作为可恢复缓存，不参与业务决策。
- 添加账号：创建远端行、本地缓存、前台 profile 和后台 profile，全部成功才显示“已添加”。
- 删除账号：使用持久化删除状态机依次停止调度、撤销租约、释放 WebView、清理对应 profile 与缓存、完成数据库墓碑记录；跨数据库、进程与文件系统的步骤不能声称由同一 SQLite 事务原子完成，失败可恢复且不能误删客户主档。
- 切换账号：只切换前台 WebView 和辅助数据，不改变其他账号的后台租约。
- 状态事件必须带 `accountId`；UI 只更新对应账号行，禁止整页重绘。
- 账号列表显示最后心跳、采集覆盖、最后错误和待处理任务，不以“当前账号”代替全部账号状态。

## 9. 采集与群组监测

### 采集规则

- 会话列表同步、实时消息、完整历史分开计数。
- 未读会话不打开、不滚动、不改变已读状态。
- 一对一会话按现有规则进入客户链路。
- VIP 群和明确绑定的群组按既有业务规则处理；普通群和类型不明会话不进入客户提醒。
- 群事件必须记录原始来源、群 JID、账号、成员、事件类型、时间和来源游标。

### 覆盖率

采集卡片显示“已发现列表数、已完成历史数、跳过未读数、待重试数、无法验证数”。如果 WhatsApp 页面只暴露当前渲染窗口，界面必须标记为“页面可见范围”，不能伪称全量完成。

### 渠道

每个群组保存 `sourceDefinitionId`、`channelId`、`channelLabel` 和 `groupFanType`。缺少来源定义时显示“未分类，待绑定”，不能默认覆盖成泛化“群粉”。

## 10. AI 队列与客户档案

- 完整历史落库后才创建 AI 任务。
- 长对话使用服务端 cursor 分段，按 provider 限额并发；每段保存 checkpoint 和输入哈希。
- AI 输出必须包含客户 ID、消息证据、字段、旧值、新值、置信度、模型、时间和冲突原因。
- 只补已唯一匹配客户的空字段；人工锁定字段和已有非空字段不覆盖。
- 资金实力和聊天粘度进入跟进优先级；工作、投资年限等只补客户资料，不直接生成跟进优先级。
- 低置信度、冲突和缺少证据的结果进入人工确认队列。
- AI 服务不可用时保留原文和任务，显示可重试状态，不显示虚假成功。

## 11. 设备迁移与便携使用

### 目标

应用安装包不依赖固定电脑路径、机器名或固定端口；任何受支持的 Windows 设备都可以安装使用。业务数据通过设备迁移包移动，而不是依赖旧电脑上的目录。

### `.zkdevice` 设备包

包含：

- 客户主档、跟票、报名、入金、跟进、任务和设置。
- WS 账号显示信息、联系人、群组、成员事件、会话、双方消息和 AI 证据。
- 群监测目标、翻译记录、群发队列和发送审计。
- 媒体原文件、媒体索引、不可用媒体状态。
- 版本、schema、行数、SHA-256 清单和导出水位。

不包含：

- WhatsApp Cookie、Token、密码、WebView 登录态。
- AI API Key 和 Windows DPAPI 密文。

### 安全与恢复

- 设备包使用用户密码派生密钥（scrypt/Argon2id）和 AES-256-GCM 加密。
- 导入先解密、校验 manifest、校验空间和 schema，再写入临时数据库；失败不触碰现有数据。
- 导入报告逐段列出恢复、跳过、冲突和不可用媒体，禁止静默丢失。
- 默认导入到空的 6.1 工作区；已有数据导入必须先 dry-run 并显示冲突。
- 新设备需要重新扫码每个 WS 账号，并重新配置 AI Key。
- 安装器提供 WebView2 Runtime 检查和在线/离线安装说明。

## 13. 性能和资源预算

### 目标指标

- 3 个账号同时后台运行时，前台聊天 30 分钟无焦点变化、滚动变化、WebView 重绘抖动。
- 5 个账号在配置的槽位内公平轮换，不允许某账号无限期饥饿。
- 本地客户搜索和筛选使用服务端分页，目标 p95 小于 300ms（测试数据集需记录）。
- 100,000 条消息采用 cursor/虚拟列表，禁止一次性放入 renderer 数组。
- 24 小时后台运行记录 CPU、RSS、GPU、句柄、磁盘写入、队列深度和错误率；不得持续无界增长。
- 前台 WebView 几何只在窗口大小、DPI 或路由变化时更新，滚动和 DOM 变化不能触发 XAML bounds 修改。

### 优化手段

- `PeriodicTimer`/Worker 替代 UI Dispatcher 定时器。
- SQLite outbox 或批量追加日志替代每条消息完整重写 `pending.json`。
- SQL LIMIT/cursor/index 替代全表加载后再截断。
- UI 局部 patch 和虚拟列表替代共享状态整页 `render()`。
- collector 只观察消息容器和明确属性，使用 dirty flag 和合并扫描。
- 构建时生成资源 manifest，避免新增模块遗漏静态资源白名单。

## 17. 明确的设计决策

1. 新设备不会自动复用 WhatsApp 登录态；必须重新扫码，这是不复制敏感凭据的安全边界。
2. 后台采集首次启用账号时需要独立采集会话授权；如果用户不授权，前台聊天仍可使用，但该账号后台采集显示“未授权”。
3. 设备迁移默认导入空的 6.1 工作区；已有数据导入前必须 dry-run 并显示冲突。
4. 默认后台采集槽位为 2，允许在资源预算和实测结果支持时调整到 1–4；不以硬编码账号数保证性能。
5. 知客主侧边栏不改造；所有 WS 新入口和 WS 辅助能力只进入独立 WS 侧边栏。
6. 群组管理账号与普通 WS 聊天账号采用独立逻辑身份、任务权限和授权流程；是否可复用同一真实 WhatsApp 账号须经平台规则与真实测试确认。
7. 联系人排除只影响指定统计范围，不删除客户主档、不踢人、不改变真实群成员关系。
8. 软件可在不同合规 Windows 设备独立安装，跨设备迁移不等于多设备实时共享；后者为独立待决策能力。

# 20. 新增 P0：独立 WS 群组管理子系统（正式纳入 A+B）

## 20.1 业务定位与边界

新增“WS 群组管理”独立窗口/工作区及其下的“看群统计”页面，入口位于 WS 独立侧边栏或 WS 工作区内，不改变知客主侧边栏、原有路由顺序及现有业务功能。其目标是：在获得适当授权且 WhatsApp 实际提供可访问数据的范围内，监测选定群组的成员加入/退出、自动登记可确认的新成员、同步已有客户的群组成员状态、按导入名单排除指定联系人、对指定消息生成可验证的成员级读取统计及审计报表。

**两个独立业务链路不可混淆：**

| 链路 | 允许创建客户 | 允许修改什么 | 禁止事项 |
|---|---|---|---|
| 普通 WS 聊天采集 + AI | 否 | 已唯一匹配客户的有证据空字段；既有跟进投影 | AI 建立陌生客户、覆盖人工字段、跨客户串档 |
| 独立 WS 群组入群登记 | 是，满足确定性身份、排除及登记条件时 | 新建唯一客户主档，或更新既有客户的**指定群组成员关系**及可派生状态 | 同一人重复建档、仅凭昵称合并、退一个群就删除客户、覆盖既有渠道和人工资料 |

原文中“`WsArchiveLinker` 不创建陌生客户”仅适用于普通聊天 AI 链路；新增 `WsGroupRegistrationService` 依据独立登记规则工作，禁止把 AI 猜测作为自动建档依据。

## 20.2 独立账号登录与授权

- 独立的 WS 群组管理登录窗口，支持添加、扫码、连接状态、重新授权、暂停/恢复监测、退出登录、移除本地账号、健康检查和错误诊断。
- 群管账号与聊天账号分别保存 `accountId`、`accountRole`、`profileRef`、`authorizationState`、`monitorEnabled`、`lastHeartbeat`、`lastError`；逻辑权限和任务队列分离，共享受控的 CRM 事实数据库。
- 登录态仅由 WebView2/平台正常授权流程管理；不得复制、导出或共享 Cookie、Token、密码及 WebView 会话目录。是否允许同一 WhatsApp 账号在前台与独立群管会话并行运行必须先验证；不可用时提供清晰授权/限制状态，而非伪装在线。
- 新电脑重新扫码；用户可在任一满足最低系统要求的 Windows 设备全新安装软件。不同设备不自动共享登录态。
- 账号删除使用可恢复状态机，区分“退出登录”“移除本机账号配置”“清除本地业务数据”；最后一项必须另行确认。

## 20.3 群组选择、监测及来源

- 同步当前账号**实际可访问**的群组清单，按稳定群组 ID + 账号 ID 区分，不按名称合并。
- 支持单群或多群启用/暂停、搜索、筛选、最后成功同步、错误状态、覆盖范围、来源渠道绑定。
- 保留 `sourceDefinitionId`、`channelId`、`channelLabel`、`groupFanType`；来源缺失标记“未分类，待绑定”，不得自动归入泛化“群粉”。
- 群成员状态来自可验证的成员快照、明确的系统事件或其他获准且可靠的数据源；仅仅因为成员未在当前渲染 DOM 中出现，不得判断退群。
- 分别记录 `occurredAt`（来源明确提供的发生时间）和 `observedAt`（本机发现时间）。发生时间不可得时不得伪造。
- 对首次接入时已经存在的群成员，应区分“初始基线成员”与“新发生的入群事件”，不得把全部存量成员计入今日新进群。

## 20.4 进退群事件与状态机

每条事件保存 `eventId`、`accountId`、`groupId`、`memberSourceId`、`normalizedPhone`（仅在可验证时）、`eventType`、`occurredAt`、`observedAt`、`sourceEvidence`、`coverageState`、`processingState`、`idempotencyKey`。

事件类型至少有 `Joined`、`Left`、`Removed`、`UnknownChange`；不确定是主动退出还是被移除时不得猜测。成员关系状态至少有 `InGroup`、`LeftGroup`、`Removed`、`Unverified`、`SourceUnavailable`。支持多次进退群历史；同一事件重复发现时不得重复计数或写档。事件成功持久化、客户关联成功之后才推进 checkpoint。发生证据冲突或缺口时进入人工审核。

**状态粒度：**一名客户可关联多个账号下的多个群组；退群只改变对应 `(customerId, accountId, groupId)` 关系，不删除客户主档，不清除其他群组状态。客户层面的“是否仍在任何群”属于从多个关系派生的视图，不得用单一字段覆盖全部群关系。

## 20.5 新成员自动建档与全局去重

处理链路：`可验证进群事件 → 身份规范化 → 查询全局客户身份索引 → 排除/冲突判定 → 数据库事务内建档或关联 → 成员关系及事件写入 → 审计结果`。

**自动建档前置条件：**
1. 群组已明确启用自动登记；来源/渠道规则已绑定或明确指定待确认策略。
2. 具备足以安全去重的稳定身份信息，优先使用现有可信 WS 成员 ID 和已验证号码关系；不能只凭昵称。
3. 号码规范化遵守现有规则，保留原始号码和标准化号码，国际区号不能盲目补全；不可靠的号码标记待确认。
4. 该成员不在当前登记排除规则内；没有匹配冲突；数据处理具备必要授权。
5. 并发插入必须由数据库唯一约束、事务及幂等键兜底，不能只用“先查后插”。

**新客户字段：**客户 ID、原始号码（如可得）、标准化号码（如可得）、可信 WS 身份、显示名称（如可得）、首次来源账号/群组、渠道、首次登记时间、当前群组关系、登记证据、登记方式和创建时间。缺失字段保持空值，不编造。

**已有客户：**保留唯一客户 ID，追加/更新该群关系与事件历史，绝不重复建档，不覆盖人工信息、既有非空资料、来源渠道、VIP/跟票/报名/入金状态。

**异常处理：**同名不同号码、一个号码对应多个客户、多个来源身份冲突、号码不可用或身份不稳定，进入 `ReviewRequired`；不得自动错误合并。自动登记结果区分 `Created`、`LinkedExisting`、`Excluded`、`InsufficientIdentity`、`Conflict`、`Failed`、`ReviewRequired`，均可按事件追溯。

**排除规则需区分两类：**“登记排除”是显式启用的建档过滤；“看群统计排除”只影响统计分母。默认用户导入的联系人名单属于**看群统计排除**，不阻止新成员登记，除非用户另外开启登记排除。

## 20.6 联系人导入及排除名单

- 支持 CSV、XLSX，预览原始号码、规范化号码、无效、重复、匹配、未匹配及冲突；不得改写原始输入。
- 支持名单版本、创建者、导入时间、来源文件哈希、适用范围（全局/账号/群组/单次统计任务）、启用/停用和变更审计。
- 默认仅在**指定消息读取统计**中排除名单成员；不物理删除 CRM 客户、不踢出群组、不修改成员关系、不删除历史消息。
- 成员与名单匹配必须依据已验证的号码或明确确认的身份关联；匹配不了的名单条目不得被当作已成功排除。
- 统计展示导入总量、有效号码、无效号码、重复号码、已匹配成员、未匹配号码、实际排除人数、排除后剩余人数；导出匹配报告。
- 不同名单版本生成的历史统计不可被新名单静默改写。

## 20.7 指定消息“看群”已读统计：能力边界

用户选择群管账号、目标群组、**唯一的指定消息**、统计时间点/范围、排除名单版本，创建可重复执行且有审计的统计任务。消息以可验证的消息 ID、群组 ID、发送时间及发送者定位；同内容消息不能混淆。

**重要技术门禁：**WhatsApp 对群聊消息的成员级已读回执、电话号码可见性、历史回执的可访问性可能因账号、版本、隐私设置和消息而异。必须在阶段 0 使用真实授权测试确认可访问字段；不得假设一定能拿到全体成员的读取号码，不得通过隐藏接口、绕过隐私限制或凭空推断补齐。

成员状态区分：
- `ReadConfirmed`：有可验证的该消息已读确认。
- `DeliveredConfirmed`：有送达确认，但没有可验证的已读确认。
- `NoReadConfirmation`：尚无已读证据；**不等于已证明未读**。
- `Unavailable`：来源未提供或不允许访问该成员的读取状态。
- `OutOfScope`：不属于选定统计成员范围。
- `Excluded`：按指定名单版本从统计分母排除。

只对**可验证已读且已可靠关联号码**的成员展示“已读号码”；身份无法解析则显示号码不可用，不得猜测。保存状态证据、来源、观察时间、快照版本和任务 ID。

**指标与分母：**
- `eligibleCount`：统计快照中可确认的成员集合数量，扣除可确认排除成员。
- `readConfirmedCount`：其中具有已读证据的成员数。
- `unknownCount`：没有已读确认或状态不可得的成员数，并按子类展示。
- `confirmedReadRatio = readConfirmedCount / eligibleCount`（分母为 0 时显示 N/A）。
- `observableCoverage = (readConfirmedCount + deliveredConfirmedCount) / eligibleCount` 仅作为“有状态证据覆盖率”，不能称为阅读率。

如果成员全集不可验证，明确标记 `Partial` 并展示“仅对可观察成员统计”，不得对整个群组声称准确覆盖。支持历史快照、重新查询、对比、分页和受控导出；没有真实来源时页面显示“当前账号/消息无法获取成员级已读信息”，不得用演示数据伪装。

## 20.8 独立“看群统计”页面与交互

在 WS 群组管理工作区新增以下导航页签：`账号`、`监测群组`、`进退群事件`、`自动登记`、`排除名单`、`指定消息读取统计`、`看群统计`、`诊断与日志`。

页面采用顶部账号/群组/日期筛选 + 关键指标 + 趋势图 + 可分页明细 + 右侧详情抽屉的结构，支持适配不同窗口宽度和 100–200% DPI。与知客主侧边栏完全分离，前台聊天 WebView 不因统计刷新而重载。

**总览卡片：**已授权群管账号、正在监测群组、可确认成员数、今日进群、今日退群、今日新建客户、今日关联已有客户、待审核事件、指定消息已确认读取、实际排除人数、失败任务、最后成功同步。

**报表：**按账号、群组、渠道、日期筛选的进退群趋势、成员净变化、自动登记/已有客户占比、指定消息已读证据覆盖率、监测成功率。展示基线与时间范围；今日进退群按来源可确认事件计算，不能用两次人数快照差额冒充精确进退群明细。

**明细表：**事件 ID、群组、成员标识/已验证号码、客户 ID、事件类型、发生/发现时间、来源、登记处理结果、群组关系状态、错误原因。提供搜索、排序、游标分页、导出、人工审核与重试入口。

**交互：**真实加载/空状态/错误/权限不足/数据不完整状态，操作确认和撤销机制；按钮必须连到真实服务；后台更新采用增量推送，不能重置筛选、滚动或焦点。

## 20.9 推荐模块与 IPC/领域 API

复用原有 `WsAccountRegistry`、`WsWorkerSupervisor`、`WsCollectorBridge`、`WsArchiveLinker`、`WsUiShell`；按现有仓库代码结构新增或扩展以下职责（名称仅供设计，不要求重复创建）：

- `WsGroupAccountService`：独立账号角色、授权和状态机。
- `WsGroupMonitorWorker`：群组发现、成员快照、事件证据、可恢复游标。
- `WsGroupEventProcessor`：事件去重、事件状态和覆盖范围。
- `WsGroupRegistrationService`：自动建档、全局去重、审计。
- `WsMembershipProjection`：每客户每群成员关系与派生状态。
- `WsExclusionListService`：名单导入、版本、范围与匹配。
- `WsMessageReadStatsService`：指定消息状态、分母、快照、导出。
- `WsGroupAnalyticsService`：汇总、趋势、分页查询。
- `WsGroupManagementUi`：独立群管窗口与看群页面。

所有 IPC 消息必须携带 `schemaVersion`、`requestId`、`accountId`、必要的 `groupId`、权限上下文和幂等键。通过受控本机 API/队列写入 SQLite，避免多进程无序写锁争用；后台采集不能控制前台聊天 DOM。

在原 019–024 迁移之后，新增**待代码核对后编号**的版本化迁移（以下 025–030 仅为候选编号，实施前检查仓库已有迁移）：

| 候选迁移 | 数据对象 | 关键约束 |

| 026 | `ws_group_member_identity`、`ws_group_memberships`、`ws_group_member_events` | 稳定身份、群关系唯一键、事件幂等键、时间及来源证据 |
| 027 | `ws_group_registration_audit`、`ws_customer_identity_links` | CRM 外键、可信身份唯一约束、冲突审核状态 |
| 028 | `ws_exclusion_lists`、`ws_exclusion_entries` | 名单版本、作用域、规范化号码、导入审计 |
| 029 | `ws_message_read_jobs`、`ws_message_read_evidence`、`ws_message_read_snapshots` | 消息唯一定位、快照、证据、状态枚举、幂等任务 |

## 20.11 任务恢复与可观察性

- Worker 租约、`fencingToken`、心跳、重试上限、指数退避、checkpoint、死信/待审核状态、队列背压；同一任务同一时刻仅允许一个有效执行者。
- 事件和客户更新成功提交后才推进 checkpoint；重复执行不能重复建档、重复计数或重复发送。
- 任务状态真实显示 `Queued`、`Running`、`Paused`、`Completed`、`RetryPending`、`Failed`、`ReviewRequired`、`SourceLimited`。
- 监测账号/群组显示最近心跳、最近成功、最近错误、来源覆盖范围、队列深度、失败次数；敏感电话号码在日志中按需要脱敏。

## 20.12 隐私、权限与操作审计

- 仅处理经适当授权可访问的群成员、电话号码及消息状态；不得绕过平台隐私限制、隐藏接口或反自动化限制。
- 默认最小化采集和保留；导出号码名单需权限检查、范围提示、审计记录与适当保护。
- 角色分离：普通聊天操作员不自动获得群管账号管理、排除名单编辑或读取统计导出权限。
- 所有人工修正、名单变更、登记失败重试、客户关联变更、导出均保留审计；不在日志或迁移包中泄露登录凭据。

## 20.13 设备迁移包扩展

原 `.zkdevice` 设计保持不变，**增加**群管账号的非敏感显示配置、监测目标、群成员身份与关系、进退群事件、登记审计、可信身份关联、排除名单及版本、指定消息统计任务/证据/快照、看群报表历史、相关配置与审计。迁移前建立一致性快照，使用加密与 manifest/媒体哈希校验；目标设备 dry-run、冲突预览、失败恢复，成功后重新扫码授权，不迁移 Cookie、Token、WebView 登录态或 AI Key。

## 20.14 独立 Windows 安装与多设备同步边界

**P0 已确认目标：**任何满足明确最低系统要求的 Windows 10/11 x64 电脑，可下载正式安装包后独立安装、初始化空数据库并运行完整软件；不得依赖开发机、固定硬件 ID、固定用户名、固定路径、固定端口、Visual Studio、Node.js 开发环境或开发服务器。安装包必须包含或正确安装可再分发依赖、sidecar、Worker、群管和看群模块，自动检查 WebView2 Runtime；数据与安装目录分离；在干净电脑执行真实安装、升级、卸载和异常恢复验收。

**尚未授权的扩展目标：**多台电脑同时操作**同一业务工作区并实时同步**。当前本机 SQLite + `.zkdevice` 仅提供独立安装和手动迁移，不提供自动实时共享。若后续明确要求实时同步，必须单独设计用户身份/工作区、中心服务、授权、加密传输、离线队列、冲突合并、全局去重、删除传播和多端审计；未经批准不得悄悄加入云依赖，也不得宣称已经实现实时同步。

## 20.15 阶段 0 的新增真实可行性门禁

除原第 14 节阶段 0 验证项外，必须使用授权测试账号和测试群组确认：
1. 独立群管登录是否稳定，是否会干扰原 WS 聊天。
2. 能否可靠识别群组稳定 ID、成员身份和可验证号码。
3. 是否能观察真实加入/退出/移除事件，哪些事件只能由快照推断。
4. 能否定位唯一的指定消息，是否能取得成员级已读/送达证据，覆盖范围和限制是什么。
5. 断网、休眠、重启、扫码失效、DOM 变化时如何恢复，是否会把存量成员误记为新进群。
6. 进群登记与 CRM 现有号码规范、渠道、唯一约束能否兼容。
7. 在 2–5 账号、30 分钟前台聊天和 24 小时后台监测下的真实资源占用。

输出一张能力矩阵：`可验证并实现 / 部分可实现 / 受平台限制 / 未验证`，逐项附实际测试环境、证据、限制和替代 UI 状态。任何无法验证的成员级已读能力不得作为已经交付的功能。

## 20.16 新增功能验收矩阵

| 场景 | 必须达到的结果 |
|---|---|
| 新成员首次入群且身份可信 | 仅创建一个客户主档，正确关联来源群组与渠道 |
| 已有客户加入新群 | 不建新档，只新增/更新对应群关系 |
| 同一号码多种格式、跨账号、并发事件 | 不重复建档；身份冲突进入人工审核 |
| 退出一个群但仍在其他群 | 仅更新退出群关系，其他群和客户主档不受影响 |
| 首次同步大量存量成员 | 建立基线，不计入当日新入群事件 |
| DOM 缺少成员或来源不完整 | 不臆断退群，标记覆盖不完整 |
| 导入联系人排除名单 | 正确匹配、预览、版本化；不删除客户、不踢人 |
| 排除后统计指定消息 | 分母正确，已读有证据，未知不算已证明未读 |
| 已读信息不可访问 | 显示来源限制，不显示虚假号码或假已读率 |
| 多群/多账号连续监测 | 可恢复、无重复事件、前台聊天不抖动 |
| 看群统计 | 卡片、趋势、明细、导出数字一致，筛选可追溯 |
| 第二台干净 Windows 设备 | 安装、登录、迁移、群管和看群页面真实可用 |

## 20.17 与原阶段计划的整合顺序

原第 14 节的 0–6 阶段为**架构基线**，新增功能作为每阶段明确的交付子任务纳入，不得遗漏：

- **阶段 0**：原 Worker/IPC/前台隔离验证 + 独立群管授权、进退群事件、成员号码、指定消息已读可用性实测。
- **阶段 1**：账号权威与状态机 + 群管账号角色、独立登录窗口、群组监测调度与权限。
- **阶段 2**：消息/群组事实表 + 进退群事件、成员关系、登记服务、全局去重、渠道来源及人工审核。
- **阶段 3**：设备包/恢复 + 新增群管、名单、统计数据和媒体关联的迁移验证。
- **阶段 4**：领域 API/AI/性能 + 排除名单、指定消息证据统计、看群报表、查询分页和资源控制。
- **阶段 5**：WS UI/UX + 独立群管窗口、看群统计、图表/明细、状态反馈和 DPI 适配。
- **阶段 6**：真实 WS、真实群组、真实消息回执、CRM 去重、长跑、干净设备安装与发布门禁。

其中**前台抖动/焦点/滚动 P0 问题应在阶段 1–2 优先修复**，不得等到阶段 5 才处理。每阶段需提交代码变更清单、数据库差异、测试命令与真实结果、失败恢复方案和未验证事项；未获得确认不得对生产业务数据执行高风险修改。

## 20.18 仍需业务确认的配置项（不阻塞设计文档形成）

1. 默认“排除联系人”仅用于看群统计，**不影响自动建档**；若希望同时排除登记，需显式配置。
2. 自动登记默认只对监测启用后的**新进群事件**执行；是否对首次发现的存量成员批量补登，需要单独确认和预览。
3. “看群读取号码”仅指平台实际可验证的指定消息已读成员及其可见号码；不等于破解或取得隐藏号码。
4. **跨电脑独立安装 + 迁移**为已确认需求；**多电脑实时共享同一数据库**尚待单独决策。
5. 群管账号是否与普通 WS 聊天账号共用真实 WhatsApp 身份，需先验证平台允许的授权模式及会话稳定性。

## 20.19 最终交付门禁

只有第 6.1 节旧队列/AI 映射与单写入者切换门禁，以及原第 15–19 节的回归、性能、迁移和干净设备安装全部通过，并且本节的独立登录、群成员事件、自动登记、全局去重、成员关系、排除名单、指定消息统计、看群统计及真实能力边界完成验收，才能将对应功能标记“已完成”。若平台限制导致某项成员级数据不可获取，必须在产品和验收报告中如实说明，不能用模拟数据或无证据推断替代。软件正式发布仍须满足原第 19.7 节全部 P0 门禁。
