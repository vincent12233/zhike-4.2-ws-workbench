# 知客整体换代重构设计方案（方案 C）

日期：2026-11-08  
基线版本：4.4.24  
状态：用户已确认“桌面客户端 + Docker 服务端”方向，进入实施计划阶段；编码前仍需完成计划确认

## 1. 设计目标

在不丢失现有客户数据、不改变当前业务逻辑和统计口径、可随时回滚到 4.4.24 的前提下，只替换知客的技术实现和运行方式，建立下一代桌面架构，解决以下长期问题：

- 大文件单体耦合导致的回归风险；
- 整份 JSON 状态写入导致的卡顿和冲突；
- 混合导入、快速录入和日期字段识别不稳定；
- 跟票、入金、VIP、任务等业务记录边界不清；
- WS 采集、手机同步和 AI 分析缺少持久化任务链路；
- 小窗口、缩放、BrowserView 和侧栏布局不稳定；
- 备份、覆盖升级、卸载和回滚缺少完整的发布闭环。

“整体换代”指重建技术内核和桌面界面，不是重新设计业务。4.4.24 的字段含义、页面职责、统计公式、状态映射、重复判断、导入口径和 AI治理边界都是新版的兼容基准。4.4.24 保留为回滚基线，旧版功能和数据在切换完成前继续可用。

## 1.1 业务逻辑兼容合同

新版必须把当前 4.4.24 当作行为基准（golden oracle）：

- 首页数字、客户名单、筛选结果和统计口径必须与 4.4.24 一致；
- 客户字段含义、渠道/状态/阶段映射、登记日期和下次跟进日期语义不得改变；
- 跟票、入金、VIP、报名、任务和看板的记录边界、重复规则和操作顺序不得改变；
- 同一客户不同股票、方向或日期的现有分离规则必须原样保留；
- 快速录入、文件导入、批量操作、删除/恢复和同步的成功/失败语义必须保持一致；
- WS、AI档案和提醒只能在已确认的增强范围内增加能力，不得静默改变原有客户数据；
- 新版对同一隔离输入运行后，关键输出必须通过旧版快照对账；
- 任何业务规则变化必须单独列出、说明原因、提供迁移和回滚，并取得明确确认。

## 2. 当前项目事实

以下结论来自当前源代码和测试，不是推测：

- 桌面运行时为 Electron 45.2.1、Node.js 24.22.1；
- 当前 4.4.24 的本机数据库为 SQLite，现有核心状态仍包含 `app_state` 整体 JSON；新版不再把 SQLite 作为主数据库，仅将其作为迁移和回滚来源；
- `app.js`、`server.mjs`、`ws-workbench.js` 承担了大量渲染、状态、接口和业务逻辑；
- WS 使用独立 BrowserView 分区，当前采集主要依赖可见页面 DOM 和前端定时器；
- 当前版本已有 WS 多账号、断点、AI档案治理、备份和跟票多股票分离能力，但部分能力仍是合约测试或合成数据验证；
- 上次记录的全套回归为 48/48 通过，安装包测试为 2/2 通过；旧版覆盖升级因缺少可验证的旧安装包仍未完成真实验证；
- 当前工程工作区存在既有未提交修改和 4.4.24 发布文档，本次设计不覆盖、不重置这些内容。

## 3. 非目标和硬约束

### 非目标

- 不绕过 WhatsApp 验证、验证码或平台权限；
- 不读取或保存 WhatsApp 密码、Cookie、二维码和秘密 Token；
- 不承诺在平台不提供能力时实现服务端级别的“关闭电脑后全量同步”；
- 不自动发送付款、退款、密码、验证码、价格保证、法律或医疗承诺等高风险内容；
- 不开发团队协作、多租户云端后台或公开 SaaS 服务。

### 硬约束

- 现有客户、业务记录、统计口径和用户数据必须可迁移、可校验、可回滚；
- 新功能失败时，旧版知客仍可启动和使用；
- 所有数据库改动有版本化迁移；
- 不使用演示数据污染用户库；
- 任何“已同步、已保存、已提醒”状态必须有可追溯证据。

## 4. 目标架构

新版采用 WinUI 3 原生桌面外壳。主业务界面使用 WinUI 3 原生页面和控件；WebView2 只用于桌面应用内嵌的 WS 登录、聊天和账号 Profile，不提供浏览器网页版管理端。

```text
WinUI 3 Desktop App
├─ Native customer/operations UI
├─ Native WS account and AI panels
├─ WebView2 WS Host (per account profile)
├─ HTTPS API client
├─ Windows notifications
└─ Update / Backup / Recovery Controller

Docker Server
├─ PostgreSQL
├─ API
├─ AI Worker
├─ WS Connector Worker (per account)
├─ Backup/Migration Job
└─ Internal service network

Application Services
├─ Customer Service
├─ Business Record Service
├─ Import Classification Service
├─ WS Collection Service
├─ AI Analysis Service
├─ Follow-up/Reminder Service
├─ Backup/Restore Service
└─ Audit/Conflict Service

Persistence
├─ PostgreSQL repositories and migrations
├─ Legacy SQLite compatibility reader
├─ Outbox / job queue
├─ Idempotency and revision tables
├─ Legacy compatibility adapter
└─ Export/import and recovery journal
```

推荐技术边界：

- 桌面主界面采用 WinUI 3/C# 原生控件；WebView2 仅嵌入 WS页面，不把业务界面发布为网页；
- WinUI 客户端和 Docker API 之间使用版本化 HTTPS 协议；
- 服务层采用明确的 repository/service/use-case 分层；
- 新版主数据库采用 PostgreSQL，所有客户、业务记录、WS消息、AI任务和审计数据通过 repository/service 层访问；
- 旧版 SQLite 只读兼容层只用于迁移、对账和回滚，不允许新版业务直接继续写入旧 `app_state`；
- PostgreSQL、API、AI Worker 和 WS Connector Worker 默认使用 Docker Compose；
- 桌面端通过 HTTPS 调用 API，离线时保留明确的本地缓存和待上传队列；
- 桌面端与本地 WebView2 WS会话之间只通过受控的本机桥接，不读取密码、Cookie、二维码或秘密 Token。

## 5. 数据迁移和兼容方案

### 5.1 SQLite → PostgreSQL 双库影子迁移

不直接改写旧库。首次启动新版本时：

1. 自动创建不可覆盖的 SQLite 升级前备份；
2. 启动或检测 PostgreSQL 实例，并验证连接、版本和权限；
3. 读取旧版 `app_state`、客户表、WS表和迁移记录；
4. 写入新的 PostgreSQL 规范化表和索引；
5. 生成迁移清单、源记录指纹和冲突报告；
6. 只在校验通过后标记为“可切换”。

升级期间保留：

- `workspace.sqlite`：4.4.24 兼容库，只读保留；
- PostgreSQL 数据库：新架构主库；
- `migration-manifest.json`：记录每条旧记录到新记录的映射；
- `upgrade-journal.jsonl`：记录迁移、回滚和重试事件。

### 5.2 统一数据模型

新模型至少包含：

- `customers`：客户主档；
- `customer_identifiers`：电话、账号、WS会话标识等多种身份；
- `business_records`：跟票、入金、VIP、报名等业务记录；
- `messages`：原文、翻译、来源账号、会话和消息指纹；
- `ai_observations`：字段级分析结果、来源消息、置信度和时间；
- `followup_tasks`：跟进任务、提醒、处理状态和去重键；
- `import_batches` / `import_rows`：导入批次、原始行、识别结果和审计；
- `outbox_jobs`：WS采集、AI分析、CRM同步和提醒任务；
- `audit_events`：增删改、恢复、冲突和回滚审计。

客户去重和业务记录去重分开：

- 客户优先按 WS唯一标识、电话号码、账号/会话标识匹配；
- 业务记录必须同时考虑客户、股票/产品、方向、登记日期、下次跟进日期和来源批次；
- 同一客户购买不同股票，必须生成不同业务记录；
- 同一客户买入和卖出，必须生成不同记录；
- 同一客户的不同跟进周期不得被覆盖。

### 5.3 兼容导出和回滚

切换前使用兼容适配器：

- 新架构写入新库；
- 过渡期生成旧版可读取的 SQLite 导出快照，不对旧库做无审计的直接写入；
- 每次写入记录 revision 和幂等键；
- 回滚时可以恢复到升级前 SQLite 备份，或按升级日志导出 PostgreSQL 中已确认的新数据；
- 未通过迁移校验时禁止自动切换。

### 5.4 PostgreSQL 部署模式

提供两种正式部署模式，数据库结构和 API 保持一致：

- **Docker 模式**：使用 `compose.yaml` 启动 PostgreSQL 和本机服务，数据放在明确命名的持久化卷中；适合开发、测试和需要隔离环境的使用者。
- **Windows 服务模式**：由安装程序安装或连接本机 PostgreSQL 服务；适合不希望依赖 Docker Desktop 的个人生产环境。

无论哪种模式，安装程序都必须在启动前检查数据库可用性，并提供“连接失败、启动服务、备份、恢复和切换数据库”的明确提示。不得把未挂载持久化卷的临时容器当作正式数据目录。

### 5.5 已确认的 Docker 服务器版

本项目采用“服务器核心 + WS 连接器”架构：

```text
Docker Compose
├─ PostgreSQL（主数据）
├─ API（认证、客户、业务记录、WS接入）
├─ AI Worker（分析、档案同步、跟进提醒）
├─ Backup/Migration Job
└─ WS Connector Worker（按账号隔离的浏览器运行时）

Windows 桌面端
└─ WinUI 3 原生知客 + WebView2 WS Connector（可作为本地连接器）
```

WS 连接器无论运行在本机还是 Docker 中，都实现同一套版本化接入协议。每个 WS 账号使用独立的持久化浏览器 Profile/卷；用户必须通过可见登录界面自行扫码或登录。连接器不得读取密码、Cookie、二维码原文或秘密 Token，不绕过验证码和平台验证。

服务器版只将“已经由用户授权并被连接器采集到的内容”送入 PostgreSQL、AI 和提醒流水线。若平台或页面结构不支持后台读取，系统必须显示覆盖范围和最后成功时间，不能宣称服务器已获取全部历史对话。

Docker 生产部署必须包含：命名卷或绑定目录、PostgreSQL健康检查、API等待数据库就绪、账号级 WS Profile 持久化、备份卷、日志脱敏、HTTPS 和访问控制。PostgreSQL 5432 只允许在内部网络或本机管理端口访问。

## 6. 智能导入和快速录入重做

采用统一解析管线，不再让 CSV、Excel、粘贴文本和快速录入各自维护一套规则：

1. 原始输入保存为不可变批次；
2. 识别列/文本角色，不依赖前后顺序；
3. 识别登记日期、下次跟进日期、股票代码、方向、渠道、状态、客户身份；
4. 支持混合业务数据和同一号码多条业务记录；
5. 生成字段级置信度和冲突说明；
6. 预览后一次性提交；
7. 提交采用事务和幂等键；
8. 失败只回滚当前批次，不影响旧数据。

日期字段严格分离：登记日期不是系统当前日期，下次跟进日期也不覆盖登记日期。无法识别时进入待确认，而不是静默填入当天。

## 7. WS 工作台重做

### 7.1 账号和窗口

- 多账号使用同一工作台标签页；
- 每个账号独立 BrowserView 分区；
- 状态区分“持久化状态、运行状态、最近探测时间和会话过期”；
- 账号列表采用缓存优先和后台校验，避免首次为空；
- 左右侧栏可收起，中心聊天区域优先保证可用宽度；
- BrowserView 固定在工作台内部，不随主页面滚动；
- 使用版本化 bounds 协议，窗口缩放后统一重算。

### 7.2 采集链路

```text
可见 WS 页面
→ 会话列表扫描
→ 消息指纹去重
→ checkpoint
→ 本地落库
→ AI 分析队列
→ 客户档案同步
→ 跟进任务/提醒
```

所有步骤都可重试、可暂停、可恢复，并显示当前覆盖范围。平台不允许隐藏页面读取时，界面必须明确显示限制，不伪造“全量同步成功”。

## 8. AI 和客户档案

- AI分析结果以字段级 observation 保存，而不是直接覆盖客户档案；
- 每个字段保存来源消息、置信度、分析时间和当前值；
- 已有人工内容默认不覆盖；冲突进入待确认；
- AI可自动新增客户、补齐空字段、修改允许自动修改的低风险字段、移入回收站；
- 永久删除仍需二次确认；
- AI请求进入持久化队列，支持超时、重试、格式校验和失败恢复；
- 跟进提醒使用去重键，避免同一客户同一原因重复提醒；
- AI分析失败不阻塞聊天、导入和客户保存。

## 9. 性能目标

目标在真实 PostgreSQL、真实窗口和合成 10,000 / 50,000 客户数据上分别测量：

- 搜索、筛选和分页 P95 控制在 300ms 级别；
- 连续输入不触发明显长任务；
- 列表使用虚拟化，DOM 行数保持在可控范围；
- 状态写入从整份 JSON 改为增量提交；
- 所有轮询使用统一调度器、单飞锁和退避；
- WS采集和AI分析显示队列长度、耗时和失败原因。

## 10. 发布、升级和回滚

### 阶段切换

1. 新版只读影子运行，对比旧版结果；
2. 新版灰度写入测试数据；
3. 在用户确认迁移报告后切换新库；
4. 保留旧库和旧版安装包；
5. 经过多轮回归后才将新版本设为默认。

### 回滚条件

出现以下任一情况自动停止切换：

- 迁移记录数不一致；
- 客户或业务记录指纹不一致；
- 统计口径发生未批准变化；
- WS账号或消息数据无法恢复；
- 备份恢复演练失败；
- 关键页面出现未处理异常。

## 11. 验收标准

### 数据

- 旧版客户、跟票、入金、VIP、任务、WS和设置可迁移；
- 同一客户不同股票、方向和日期不合并；
- 导入失败可回滚，重复提交不重复写入；
- 删除、恢复和同步均可追溯。

### WS/AI

- 多账号切换和重启状态恢复正确；
- 已授权范围内的消息可断点采集和去重；
- 手机新消息到工作台的实际延迟可测量；
- AI档案、跟进任务和提醒不重复、不误报；
- AI或WS失败不影响知客其他页面。

### 界面和性能

- 820×540、900×600、1024×768、1366×768及125/150/200%缩放下关键操作可达；
- WS中心区域不被侧栏或主页面滚动遮挡；
- 10,000和50,000客户规模下搜索、筛选、保存和切页无明显卡顿。

### 发布

- 覆盖升级保留数据；
- 卸载和换机恢复符合说明；
- 备份可恢复；
- 失败可以回滚到4.4.24；
- 安装包测试不能只以“编译成功”作为通过条件。

## 12. 实施顺序

1. 冻结 4.4.24 并生成升级前备份；
2. 建立新数据模型、迁移器和兼容适配器；
3. 实现统一导入与业务记录服务；
4. 实现统一任务队列、事务、幂等和审计；
5. 实现新客户/任务/业务记录页面；
6. 实现 WS新工作台和消息采集服务；
7. 接入 AI 档案、跟进提醒和通知；
8. 接入性能优化、备份、升级和回滚；
9. 运行合成数据、窗口、安装和真实授权 WS 测试；
10. 生成安装包、测试报告、已知限制和回滚说明。

## 13. 需要用户确认的决策

在开始编码前，需要确认以下默认选择：

1. Docker 服务器是否部署在当前 Windows 电脑、局域网主机或云服务器；
2. WinUI 3/WebView2 本地连接器是否作为 Docker WS 连接器的备用入口；
3. 新版是否先以独立服务器栈并行验证，再迁移正式数据；
4. WS真实链路测试是否继续使用当前用户已授权的个人账号和测试联系人。

默认建议：PostgreSQL、API、AI Worker 和按账号隔离的 WS Connector Worker 使用 Docker Compose；WinUI 3 原生桌面应用作为唯一用户界面，WebView2 只承载 WS；先独立服务器栈验证，再迁移正式数据；通过用户主动发送的测试消息做真实链路验收。
