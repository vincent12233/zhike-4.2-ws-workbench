# Zhike 6.0.3 一次性稳定升级设计

## 目标

在现有知客业务规则和 WinUI + WebView2 + Node SQLite 运行链上完成一次整体升级，交付可长期运行的 6.0.3：WS 登录后可独立发现和监测群组，后台采集不干扰前台聊天，AI 对完整消息进行结构化分析并补齐已有客户，翻译和群发任务可控可追踪，所有工作区使用同一条数据链，滚动和窗口布局稳定，代码按领域拆分且不继续扩大屎山。

## 非目标

- 不恢复 Docker、PostgreSQL、Electron 或旧客户端。
- 不复制第三方聚合翻译软件或云控的实现、协议或品牌。
- 不改变客户、VIP、跟票、报名、入金、统计和手机号登记的业务含义。
- 不自动覆盖低置信度或冲突的客户字段。
- 不因普通聊天分析无条件新建客户。

## 已确认约束

- 仍然只使用 WinUI 3 + WebView2 + 随包 Node SQLite。
- 业务记录保持独立，但手机号关联客户主档案。
- WS 前台可以正常聊天；后台采集使用隔离 Collector，不滚动、点击或切换前台聊天。
- 未读会话自动跳过；审核中的群成员不计入已进群。
- 群聊可采集并分析，但群聊与一对一会话在数据上区分。
- 群组监测与 VIP 管理分离；群组事件可补齐已有或新进群客户档案。
- AI 只补齐已有客户的空字段；低置信度和冲突进入人工确认。
- 跟进优先级由 AI 分析资金资质和聊天粘度，工作、投资年限等只补档。

## 设计方案

### 方案 A：继续全量状态 Blob 加补丁

改动小，但保存、渲染和并发问题会继续扩大，不采用。

### 方案 B：在现有项目上建立 6.0.3 领域核心（采用）

保留现有业务页面和规则，通过稳定的领域服务和事实表连接客户、WS、群组、AI、任务；逐步把全量状态写入降为设置和兼容入口。采用此方案是因为它不破坏已有业务，同时可以消除重复逻辑、全量重绘和前后台耦合。

### 方案 C：完全重写新客户端

可获得最干净的代码，但会重新实现大量已验证业务并增加回滚风险，不符合“保留原业务规则”的要求。

## 核心架构

1. `ws_accounts`：账号和连接状态。
2. `ws_conversations` / `ws_messages`：会话和消息事实，消息使用账号+会话+外部 ID 幂等。
3. `ws_group_catalog`：账号级完整群组目录。
4. `ws_group_monitor_targets`：监测配置，使用稳定 channelId 和 groupJid。
5. `ws_group_membership_events`：进群、退群、移除、待审核等不可变事件。
6. `customer_group_memberships`：客户与群组的多对多关系。
7. `ai_jobs` / `ai_field_evidence`：AI 队列、证据、置信度和冲突。
8. `followup_tasks`：今日工作台、任务中心和阶段看板统一读取。
9. `translation_jobs` / `broadcast_jobs`：翻译和群发的队列、取消、限速、审计。
10. 前端只订阅增量变化，不把所有模块重新序列化成一个大对象。

## 性能原则

- 前台 WebView 和后台 Collector 不共享 DOM、滚动状态或窗口尺寸。
- 原生 UI 线程只提交 WebView 操作，不做重 JSON 解析和批量聚合。
- 每个滚动区域只有一个垂直 scroll owner。
- 客户、消息、任务和导入列表使用真实分页或虚拟列表。
- 只读请求可以合并，但每个调用方仍可取消。
- 所有后台任务有队列长度、耗时、失败、重试和资源指标。
- 24 小时运行必须有内存、CPU、磁盘和队列增长告警。

## 用户体验升级

- WS 顶部显示账号、连接、后台采集、暂停、重连和队列状态。
- 右侧辅助面板使用可收缩抽屉，关闭后释放列宽。
- 翻译模式支持接收翻译、发送翻译、显示原文、双语模式。
- 群发采用任务草稿、预览、限速、暂停、取消、失败重试和发送审计。
- 群组监测显示已发现群组、已配置群组、最后同步、成员变化和异常。
- 所有 AI 结果都可以追溯到消息证据和字段变更。
