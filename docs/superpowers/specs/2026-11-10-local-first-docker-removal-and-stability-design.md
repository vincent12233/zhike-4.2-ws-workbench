# 知客本机单一存储与稳定性大升级设计

## 意图

把知客整理为一套稳定的 WinUI 3 桌面应用：业务数据、导入、WS、AI、快照和提醒全部使用同一个本机 SQLite 工作区，不再依赖 Docker Desktop、PostgreSQL 容器、配对码或网络连接。保留现有页面体系和业务口径，只替换不稳定的存储边界并统一界面壳层。

## 当前证据

- `resources/app/server.mjs` 已提供本机 SQLite、WAL、迁移、快照、工作区锁和大部分业务 API。
- WinUI 当前本机模式仍会让页面使用 WebView `localStorage`，Docker 模式才使用 API bridge，形成双存储路径。
- 当前 WinUI bundle 不包含 `node.exe`，因此不能直接把 `server.mjs` 当作已部署的桌面本机服务。
- `resources/app/styles.css`、`v4.css`、`v41-ui.css`、`design-system.css`、`ui-refresh.css` 等多份样式重复覆盖侧边栏；`.nav-groups` 缺少 `min-height:0`，`body` 还存在 `min-width:1100px`，这是滚轮和小窗口溢出的主要根因。
- 当前自动回归有 76 项，但缺少真实 20 路由点击、滚轮、存储持久化和桌面窗口交互测试。

## 目标

1. 本机 SQLite 成为唯一权威存储，应用离线时仍可完整使用。
2. 删除 Docker/ PostgreSQL / 配对连接作为正式产品能力及其运行时代码。
3. 现有客户、手机号登记、热聊、群组、VIP、跟票、报名、入金、统计、数据中心、设置、WS 和 AI 功能继续可用，业务规则和统计口径不变。
4. 侧边栏、主内容区、弹窗和 WS 页面在常用窗口与 DPI 下稳定可操作。
5. 所有写入具备事务、快照、冲突保护、错误可见性和可恢复性。
6. 交付一个唯一的 WinUI 安装包，不再把 Electron 或 Docker 版本作为日常入口。

## 非目标

- 不把项目改造成网页版或云端 SaaS。
- 不改变客户主档案、跟票买入/卖出分离、手机号登记独立等现有业务规则。
- 不在没有备份和校验的情况下物理删除用户数据、Docker 数据卷或历史安装包。
- 不在第一阶段重写 AI 提示词、WS 登录策略或页面业务语义；这些只做稳定性适配。

## 方案比较与选择

### 方案一：本机 C# SQLite API

由 WinUI 直接使用 `Microsoft.Data.Sqlite`，重写现有 API bridge 和本机服务。进程最少，但需要重写大量现有 Node API、WS、AI、导入和快照逻辑，回归风险最高。

### 方案二：WinUI 托管受控 Node SQLite sidecar（采用）

复用已经存在且经过测试的 `resources/app/server.mjs`，随 WinUI bundle 携带固定版本的 Node runtime。WinUI 负责启动、健康检查、端口选择、父进程退出、日志隔离和异常重启；页面始终通过 `127.0.0.1` 的本机 bridge 访问 SQLite API。Docker 只作为迁移来源，不再进入正式运行链路。

采用理由：能最大限度保留现有业务逻辑和测试资产，避免再造一套 API；本机服务不依赖 Docker、网络或 PostgreSQL，且可以继续使用现有 WAL、快照、迁移和工作区锁。

### 方案三：继续以 Docker 为默认

只增加重连和健康检查，不能解决 Docker Desktop、端口、容器启动和配对流程造成的不稳定，放弃。

## 目标架构

```text
WinUI 3 主进程
  ├─ LocalServiceManager（启动/守护受控 Node runtime）
  ├─ LegacyBridge（统一转发到本机 SQLite API）
  ├─ WS WebView2（仅负责用户登录和可见聊天交互）
  └─ 窗口/路由/错误边界
          │ 127.0.0.1 + 随机空闲端口 + 本机 token
          ▼
受控 node.exe + resources/app/server.mjs
          │
          ▼
%LOCALAPPDATA%\\Zhike\\workspace.sqlite（WAL、快照、迁移、锁）
```

本机服务启动失败时，应用必须显示明确错误并允许重试；不得悄悄退回 `localStorage`。WS 页面与其他业务页面使用同一份 SQLite 工作区。

## Docker 移除边界

迁移和回归完成后，从正式项目和安装包移除：

- `infra/compose.yaml`、`infra/compose.prod.yaml`、Docker 环境示例与容器启动脚本。
- `server/` 中仅用于 PostgreSQL、配对、服务器 API、Worker 和 PostgreSQL migration 的运行代码。
- WinUI 的 Docker 连接页、配对码、PostgreSQL 模式、`ApiClient`、Docker 分支和相关 IPC。
- Docker 专用构建脚本、迁移工具、Docker-only 测试和对应的日常文档。

保留但不打包进正式应用：一次性的只读导出/迁移工具和迁移说明，放入外部归档目录，直到用户确认本机数据校验完成。不会删除 Docker 数据卷，除非另行得到明确的物理删除指令。

## 数据迁移与回滚

1. 升级前自动创建本机 JSON、SQLite 和当前配置三份备份，并写入 SHA-256 清单。
2. 如果检测到 Docker 配置，先只读导出客户、业务记录、WS、AI 和跟进数据；不自动覆盖本机记录。
3. 以客户唯一标识、号码和会话标识去重；业务记录按独立业务 ID 保留，跟票买入和卖出不合并。
4. 导入本机 SQLite 前执行预览、数量核对和字段冲突报告；用户确认后在一个事务中写入。
5. 迁移失败自动回滚事务；安装失败或首次启动失败可使用上一版安装包和备份恢复。
6. 完成校验后删除正式项目中的 Docker 运行代码，归档包不进入安装包和默认启动路径。

## 界面与交互升级

### 壳层

- 新增唯一权威的 `resources/app/modules/shell-layout.css`，负责 `.app-shell`、`.sidebar`、`.nav-groups`、`.main-area`、`.view-container` 和断点。
- `body` 和 `.app-shell` 使用视口高度并禁止外层滚动；主内容区和侧栏各自拥有明确滚动容器。
- `.nav-groups` 固定 `min-height:0; overflow-y:auto; overflow-x:hidden; overscroll-behavior:contain; scrollbar-gutter:stable; touch-action:pan-y`。
- 统一折叠宽度、展开宽度、焦点样式、键盘导航、滚轮和触控板行为。
- 820×540、1100、1440、最大化以及 125%/150% DPI 均有明确布局断点。

### 页面模块

- 统一页面标题、筛选栏、表格、卡片、分页、弹窗、加载态、空态和错误态。
- 所有路由由统一 route registry 渲染，并使用页面级错误边界；单页异常不能阻塞导航。
- 大列表采用索引、分页和分批渲染；搜索和筛选使用防抖，不在滚轮或输入事件中重复全量计算。
- WS 工作台继续保留三栏布局、侧栏收起和消息采集；只替换数据桥接和异常处理，不改变登录方式。

## 稳定性规则

- 所有写操作：先快照、事务写入、版本检查、成功后刷新；失败显示真实原因并保留原数据。
- 导入：预览与提交分离，重复批次幂等，登记日期与下次跟进日期独立保存。
- WS：消息按账号/会话/消息 ID 去重，断点和手机同步写入同一数据库，AI 失败不能阻塞聊天。
- AI：分析结果和跟进提醒可重试，低置信度标记人工确认，不能误报成功。
- 日志：只记录诊断 ID、耗时和错误类别，不记录密码、Cookie、二维码或秘密 Token。

## 验收门禁

1. 本机服务启动、重启、端口冲突、锁恢复和应用退出均通过。
2. 20 个路由逐个点击并确认页面非空、按钮可触达、错误可见。
3. 侧栏在 820×540、125%/150% DPI 下滚轮和键盘滚动均改变 `scrollTop`。
4. 客户、手机号登记、混合导入、跟票、入金、删除、恢复、备份和回滚通过隔离数据测试。
5. WS 登录、账号切换、消息去重、断点采集、AI 分析和提醒刷新通过。
6. 1 万/5 万条隔离数据下搜索、筛选、分页和页面切换在可接受耗时内完成。
7. 覆盖升级、卸载、重装不删除 `%LOCALAPPDATA%\\Zhike` 用户数据。
8. Docker 相关运行代码不再出现在正式 bundle、安装包或默认启动流程中。

## 实施顺序

P0 数据备份与迁移工具 → P1 本机 sidecar 与统一 bridge → P2 移除 Docker 正式链路 → P3 壳层和侧栏重整 → P4 路由/模块错误边界与性能 → P5 全量回归、覆盖升级和唯一安装包交付。

## 仍需实施者决定的事项

- sidecar 使用的 Node 固定版本和本机端口分配策略。
- 归档包的外部保存位置和保留期限。
- 现有 Docker 数据是否在迁移校验完成后由用户手动销毁。

## 默认实施决定（待用户确认）

- WebView `localStorage` 与 Docker 导出都视为待保留数据源；升级首启先分别备份，再导入 SQLite。冲突不静默覆盖，生成可查看的冲突报告。
- Docker 迁移范围限定为当前电脑可访问的容器/配置，不承诺远程 PostgreSQL 迁移；迁移可以取消，未解决冲突不会提交。
- 客户、业务记录、统计、备份和设置在断网时可用；WS 登录/手机实时同步/AI 调用需要网络，断网期间进入本机队列，恢复后按幂等键重试。
- 继续使用当前 WinUI 3 + WebView2 + x64 per-user Inno Setup 交付矩阵；本机服务仅绑定 `127.0.0.1`，每次启动生成短期 token，敏感配置使用 Windows 加密存储。
- 页面请求统一经过 C# `LegacyBridge`，WebView 不直接访问本机服务；桥接层统一处理超时、错误、重试和诊断 ID。
- 默认性能门槛：冷启动到可操作不超过 8 秒；常用路由切换不超过 300ms；10k 客户搜索/筛选不超过 200ms；50k 客户不超过 500ms；批量导入以分批提交和可取消进度显示为准。
- 默认备份策略：批量写入/删除/恢复前创建快照，保留最近 20 个，快照失败则取消写入；完整导出仍由用户主动触发。
- 默认冲突策略：优先唯一客户 ID，其次规范化号码，再其次账号/会话标识；多个候选无法确定时保留原记录并要求人工确认，不自动合并。
