## 1. 结论摘要

现有项目是 Electron 45.2.1 桌面应用，界面是原生 HTML/CSS/JavaScript，后端是随包 Node.js 本机 HTTP 服务，数据库是 Node 内置 `node:sqlite` 管理的 SQLite 文件。业务状态主要保存在单条 `app_state.json` 中，客户索引同步写入 `customers` 表。

当前项目没有 WS 登录、消息、聊天会话、翻译或 WS 同步模块，也没有读取外部页面 Cookie、密码、二维码或第三方会话的代码。现有主窗口只允许加载本机页面，外部导航和窗口打开请求均被拒绝。

可以直接复用客户资料、跟进、快照、备份、GPT 请求和本机通知能力。WS 新功能应作为独立页面、独立模块和独立数据表/API 接入，不能把大量消息直接塞进现有 `app_state`，否则会放大全量写入、冲突和备份体积。

按用户描述，本报告将“WS”按 WhatsApp Web 场景评估。若实际平台不是 WhatsApp，需要在编码前替换 URL 白名单和平台说明。

## 3. 前端、后端和数据库

### 前端

- Electron BrowserWindow 加载本机 URL。
- 原生 HTML/CSS/JavaScript，无 React、Vue、构建脚本或 npm 依赖锁文件。
- `package.json` 版本为 `4.1.3`，入口为 `main.cjs`。
- 现有窗口最小尺寸为 820×540；基础 `body` 仍有较宽的最小内容宽度，新 WS 三栏需要单独做窄窗口适配。

### 后端

- 随包 Node.js 启动 `server.mjs`。
- 监听 `127.0.0.1`，端口默认 4173，冲突时在 4173–4199 内递增。
- Electron 通过环境变量注入随机 API 会话 Token、关闭 Token 和用户数据目录。
- 服务使用本机 HTTP，不对外网监听；外部 GPT 服务请求使用 HTTPS。

### 数据库

`server.mjs` 使用 Node 内置 `node:sqlite` 的 `DatabaseSync`：

- `app_state`：单行完整业务 JSON、更新时间、revision。
- `state_snapshots`：完整业务快照。
- `customers`：客户检索索引和客户 JSON。
- `schema_migrations`：当前只记录迁移版本。
- 索引：手机号、来源/助理、状态、阶段、删除标记。
- SQLite `user_version` 当前为 4，启用 WAL、外键和 5000ms busy timeout。

业务明细（跟进、跟票、入金、报名、手机号登记、活动、导入问题等）目前仍嵌在 `app_state` JSON 中，没有独立表和外键。

## 4. 当前登录、客户、消息和设置模块

### 登录系统

没有知客账号登录或用户认证系统。现有安全机制是：

- 本机服务随机 `X-Zhike-Api-Token`。
- localhost Host/Origin 校验。
- 工作目录启动锁，防止同一工作区重复启动。
- 清空全库密码只保存 SHA-256 摘要。

GPT API Key 保存到用户目录中的 `ai-credentials.json`，使用 Electron `safeStorage` 加密，不进入 SQLite、完整备份或日志。

### 客户资料

客户资料由 `app.js` 的共享 `state.customers` 承载，并通过 `/api/state` 持久化。现有字段包括客户编号、姓名、原始号码、规范化号码、来源/渠道、页面、助理、状态、阶段、资质、热聊、跟票、入金、金额、报名、跟进日期、备注、删除标记等，并允许向客户对象追加兼容字段。

现有客户去重主要使用标准化手机号；跟票和入金按客户、日期和业务字段使用记录级签名，同一客户可以有多只票或多笔入金。

### 消息和聊天

当前没有消息表、会话表、聊天页面、翻译服务或 WS 适配器。现有“热聊管理”是客户标记，不是消息模块。GPT 运营助手只处理用户主动提交的本地业务上下文或附件。

### 设置

系统设置和工作区设置保存在 `state.settings`，桌面备份/提醒配置另存于用户目录 `desktop-tools.json`。现有设置可以扩展 WS 功能开关和默认语言，但 WS 消息、译文和分析结果不应放入同一个全量业务 JSON。

## 5. 现有 API 和安全边界

实际路由：

- `GET /api/health`
- `GET /api/state`
- `GET /api/state/version`
- `PUT/POST /api/state`
- `GET /api/snapshots`
- `POST /api/snapshot`
- `POST /api/snapshots/:id/restore`
- `POST /api/import/legacy/preview`
- `POST /api/import/legacy/commit`
- `GET /api/diagnostics`
- `POST /api/shutdown`

除 health 外均要求本机随机 API Token；状态写入还要求 `X-State-Version`，版本不一致返回 409。客户端通过延迟写入、3 秒版本检查和按 ID 合并处理并发变更。

主窗口使用 `contextIsolation:true`、`nodeIntegration:false`、`sandbox:true`，并只加载本机 URL。`setWindowOpenHandler` 和 `will-navigate` 当前拒绝外部页面。没有 `BrowserView`、`WebContentsView`、`webview`、Cookie API、DOM 注入或外部导航实现。

## 10. 当前无法在现有程序中直接可靠实现的功能

如果 WS 平台没有适合个人登录的官方授权接口，当前代码不能安全、稳定地承诺：

- 后台永久同步全部会话或未读消息。
- 电脑关闭后继续接收消息。
- 自动读取外部 WS 页面全部 DOM、Cookie 或登录状态细节。
- 绕过验证码、二维码、平台安全验证或保存 WS 密码。
- 无人工确认的自动双向发送和自动发消息。

第一版可实现的安全范围是：知客内打开官方 WS 页面，用户自己登录；用户显式复制或选择当前可见聊天内容后，在知客内翻译、保留原文、做 AI 分析、生成回复草稿并由用户确认复制或发送。若平台提供官方 API，再单独设计授权和同步扩展。

## 11. 当前错误、风险和技术债务

1. 业务明细集中在单一 `app_state` JSON，若将 WS 消息直接写入会造成大 JSON、全量冲突和备份膨胀。
2. 现有快照/自动备份只覆盖业务 state；新增 WS 独立表必须同步设计导出、恢复和回滚。
3. 本机服务是 loopback HTTP；外部 WS 页面必须使用独立窗口/视图和严格 URL 白名单，不能放宽主窗口导航策略。
4. 当前没有消息幂等键、序列号和会话状态模型，需要为重复消息、乱序、刷新和断线重连单独建模。
5. 现有基础样式的最小宽度与 820 像素窗口下限不适合直接放入三栏 WS 页面，需要模块级响应式布局。
6. 当前没有 WS 平台官方接口配置，翻译服务也没有独立抽象；需要先确定使用现有 GPT 作为可选翻译/分析服务，失败时保留原文并允许手动重试。
